## 2. CLAUDE.md (그대로 복사해서 수정)

```markdown
# 프로젝트 컨텍스트

## 무엇을 만드는가

PC 견적 검증 도구. 부품 조합의 호환성·전력·전기요금을 판정한다.
가격 비교가 아니라 **판단을 돕는 도구**다. 다나와와 경쟁하지 않는다.

상세: `docs/pc-builder-spec.md`

## 작업 규칙

1. **구현 전에 `docs/pc-builder-spec.md`의 해당 섹션을 먼저 읽는다.**
   추측으로 구현하지 않는다.
2. 스펙과 다르게 구현해야 할 이유가 생기면 **먼저 문서를 고치고 승인을 받는다.**
   코드와 문서가 어긋난 채로 진행하지 않는다.
3. 설계 결정은 `docs/decisions/`에 ADR로 남긴다.
4. 조사 결과는 `docs/research/`에 markdown으로 남긴다.
5. 커밋은 작게. 한 커밋에 한 가지 변경.

## 절대 규칙

- **회원가입·로그인 기능을 만들지 않는다.** 개인정보를 다루지 않는 것이 이 프로젝트의 안전 전제다.
- **localStorage 저장 포맷은 add-only.** 필드 추가는 되지만 의미 변경·제거는 안 된다.
  서버는 롤백되지만 사용자 브라우저는 롤백되지 않는다.
- **성능 수치를 단일 점수로 만들지 않는다.** 용도·해상도 축으로 쪼개서 제시한다.
- **근거 없는 수치를 지어내지 않는다.** 데이터가 없으면 없다고 표시한다.
- 외부 데이터 출처는 `source_url`과 함께 저장한다.

## 현재 단계

Phase 0a: OpenDB 적재 + 국내 유통 매칭 + 어드민
(로드맵: `docs/pc-builder-spec.md` §11)

## 보류 중

`docs/pipeline-plan.md`는 자율 운영 인프라 설계다.
**지금은 구현하지 않는다.** 앱이 배포 가능한 상태가 된 뒤에 착수한다.
참고용으로만 읽는다.

## 기술 스택

(첫 조사 이슈 완료 후 채운다)
```

## 3. 첫 세션 프롬프트

레포 연결 후 아래를 그대로 붙여넣는다.

```
docs/pc-builder-spec.md의 §5.7을 읽고, BuildCores OpenDB 조사를 진행해줘.

작업:
1. github.com/buildcores/buildcores-open-db 를 clone
2. /schemas/ 전체를 분석해서 카테고리별 필드 목록 정리
3. 아래 세 가지를 확인 (§5.7의 "clone 직후 확인" 항목)
   - 케이스 스키마에 GPU 최대 길이 / 쿨러 최대 높이 / 라디에이터 장착 필드가 있는가
   - GPU 스키마에 AIB 모델별 물리 치수(길이, 두께)가 있는가
   - 현행 세대 부품 커버리지 — 샘플 20개를 찾아본다
4. §4.1의 호환성 규칙 8개 각각에 대해, 필요한 필드가 OpenDB에 존재하는지 대조표 작성
5. 결과를 docs/research/opendb-schema-analysis.md 로 저장

결론에는 반드시 포함할 것:
- 규칙 8개 중 OpenDB만으로 구현 가능한 것 / 수동 보강이 필요한 것
- 수동 보강이 필요하다면 그 규모 추정

코드는 작성하지 말고 조사와 문서화만 해줘.
```

## 5. 설계 문서를 세션에서 유지하는 방법

문서가 레포에 있으므로 코드와 함께 버전 관리된다. 이 이점을 살리려면 규칙이 필요하다.

### 변경 흐름

```
설계가 바뀌어야 함
      ↓
docs/ 수정 → 커밋 → 승인
      ↓
그 다음에 구현
```

**코드를 먼저 고치고 문서를 나중에 맞추지 않는다.** 문서가 뒤처지는 순간 다음 세션이 잘못된 컨텍스트로 시작한다.

### ADR 템플릿

`docs/decisions/0001-template.md`

```markdown
# ADR-000X: 제목

## 상태
제안 / 채택 / 폐기 / 대체됨(ADR-000Y)

## 배경
어떤 문제 상황인가

## 결정
무엇을 정했는가

## 이유
왜 그렇게 정했는가. 검토한 대안과 탈락 이유

## 결과
이 결정으로 생기는 제약과 후속 작업
```

### 이미 내려진 결정들 (ADR로 옮길 것)

지금까지 대화에서 정해진 사항. 레포 생성 시 ADR로 기록해두면 이후 세션이 되묻지 않는다.

```
ADR-0001  회원가입을 만들지 않는다
ADR-0002  BuildCores OpenDB를 1차 데이터 소스로 한다
ADR-0003  parts(글로벌)와 skus(국내 유통)를 분리한다
ADR-0004  성능 지표를 단일 점수로 만들지 않는다
ADR-0005  localStorage 저장 포맷은 add-only
ADR-0006  가격 비교 커머스로 경쟁하지 않는다
ADR-0007  예측 모델은 1년 이력이 쌓인 뒤 재검토 (기술통계 우선)
```

## 6. 세션 운영 메모

- **긴 작업은 이슈 단위로 끊는다.** 한 세션에서 여러 이슈를 처리하면 컨텍스트가 흐려진다
- 세션 시작 시 관련 문서 섹션을 명시적으로 지정한다. "spec을 읽어봐"보다 "§5.7을 읽어봐"가 낫다
- 조사 결과가 설계를 바꾸면 **먼저 문서 PR을 올리게 한다**
- 클라우드 세션은 실행 환경이 격리되어 있어 외부 네트워크 접근이 제한될 수 있다. 네이버 API 연동(#5)은 로컬이나 서버에서 확인이 필요할 수 있다

## 7. 병렬로 직접 할 것

Claude에게 넘기지 않는 작업.

```
□ 서버 OS 설치 및 기본 보안
□ 네트워크 구성, 방화벽  ← pipeline-plan.md §14.4.3.1
□ k3s 설치
□ 도메인 확보
□ 네이버 개발자센터 앱 등록
□ 배포 환경변수에 ADMIN_TOKEN 넣기  ← ADR-0020. 없으면 /admin이 404다
```

**방화벽 설정은 반드시 직접 한다.** 공인 IP에 6443이 열리는 사고는 한 번이면 끝이고, 지금은 브로커도 워치독도 없어 자율 운영의 전제 장치가 하나도 없는 상태다.
