# 기술 스택 — 요구사항 정리와 후보 비교

이슈 #2의 결정 재료다. **결정 자체는 사용자 몫**이다 — `pc-builder-spec.md` §9가
"백엔드: 무엇이든. **기존에 익숙한 것 우선**"이라고 두었기 때문이다. 이 문서는
선택지를 좁히고 각 안의 결과를 정리한다.

## 1. 지금까지 확정된 제약

조사와 ADR로 확정된 것들이다. 스택 선택은 이 안에서 이뤄져야 한다.

| 출처 | 제약 | 스택에 주는 영향 |
|---|---|---|
| §8 페이지 구조 | **SSR 또는 정적 생성 필수.** 검색 유입이 목적이라 CSR 단독은 불리 | 프론트 프레임워크 선택을 사실상 지배한다 |
| §8 | `/part/:slug` 롱테일이 부품 수만큼. 적재 대상 20,282건 | 빌드타임 전량 생성은 비현실적 → **SSR 또는 ISR** 필요 |
| ADR-0001 | **회원가입 없음** | 인증·세션 스택 전부 불필요 |
| §8A | localStorage + URL 인코딩이 지속성의 전부 | 클라이언트 로직 비중이 작지 않다 |
| ADR-0009 / compat-rules | 규칙 엔진 반환이 3값 + 사유 | 순수 로직. 언어 무관하지만 **공유 가능성**이 변수 |
| §5.8 | `part_specs` key-value | **PostgreSQL JSONB 권장** (스펙 §9) |
| 조사 결과 | 적재 48,207건 / MVP 20,282건 | 규모가 작다. 성능 최적화 불필요 |
| 조사 결과 | 어드민 보강 대상이 **수십 건** 규모 | 어드민을 무겁게 만들 이유가 없다 |
| §7 (Phase 2) | 상품명 정규화에 임베딩 → **Python 생태계** | Phase 2에 Python 구성요소가 들어온다 |

| §9 | 부하가 거의 없다 | 캐시·큐·최적화 전부 후순위 |

### 1.1 규모 감각

부하 관련 제약은 사실상 없다. 스펙 §9의 "최적화를 미리 하지 않는다"가 맞다.

```
부품 20,282건 · 사용자 약 100명 · 피크 시에도 초당 1건 미만
```

**스택 선택의 기준은 성능이 아니라 유지보수와 배포 단순성이다.**

## 2. 갈림길은 하나다 — 언어를 몇 개 쓸 것인가

SSR 요구(프론트)와 임베딩 워커 요구(Phase 2, Python)가 서로 다른 생태계를 가리킨다.
여기서 선택지가 갈린다.

### 2.1 규칙 엔진 공유 여부가 실질 쟁점

호환성 규칙 엔진은 두 곳에서 필요하다.

- **클라이언트** — 부품을 고르는 중 즉시 피드백 (서버 왕복 없이)
- **서버** — `/build/:hash` 공유 링크의 SSR 결과 페이지

**같은 언어면 엔진 코드를 한 벌만 쓴다.** 다르면 두 벌을 유지해야 하고, 두 구현이
어긋나면 "편집 중엔 통과였는데 공유 링크에선 오류"가 난다. 규칙이 8개에서 14개로
늘어나는 계획(§4.2)이라 어긋날 여지가 계속 커진다.

`pipeline-plan.md` §9.3이 회귀 테스트를 판정자로 세운 구조에서, **판정 로직이 두 벌인
것은 그 자체로 사각지대**다.

## 3. 후보

### 안 A — TypeScript 단일 (+ Phase 2에 Python 워커 분리)

```
프론트·백엔드   Next.js 또는 SvelteKit (SSR/ISR)
DB              PostgreSQL (JSONB)
규칙 엔진        공유 TS 패키지 — 클라이언트·서버 동일 코드
어드민           같은 앱 안의 라우트
Phase 2 워커     Python 별도 서비스 (임베딩). DB로만 연결
```

| | |
|---|---|
| 장점 | 규칙 엔진 한 벌. SSR 생태계가 가장 두껍다. 배포 단위 1개 |
| 장점 | localStorage·URL 인코딩 등 클라이언트 로직과 언어가 같다 |
| 단점 | Phase 2에 Python이 들어오면 결국 2언어가 된다 |
| 단점 | TS에 익숙하지 않다면 학습 비용이 규칙 엔진 설계보다 커질 수 있다 |

### 안 B — Python 단일

```
프론트·백엔드   Django (템플릿 + HTMX) 또는 FastAPI + Jinja
DB              PostgreSQL (JSONB)
규칙 엔진        Python 한 벌 — 서버 전용
어드민           Django admin 사실상 공짜
Phase 2 워커     같은 언어, 같은 레포
```

| | |
|---|---|
| 장점 | Phase 2 임베딩 워커까지 단일 언어 |
| 장점 | **Django admin이 §5.3 어드민 요구를 거의 그대로 덮는다.** 보강 대상이 수십 건이라 더 맞는다 |
| 장점 | SSR이 기본값이라 §8 요구를 자연히 만족 |
| 단점 | **규칙 엔진을 클라이언트에서 못 쓴다.** 부품 고를 때마다 서버 왕복. HTMX로 감당은 되지만 반응성이 떨어진다 |
| 단점 | 견적 편집 UI가 상태를 많이 가져서 HTMX만으로는 빡빡할 수 있다 |

### 안 C — 분리 (백엔드 Go·Rust 등 + 프론트 TS)

배포 단위가 둘로 늘고 규칙 엔진도 두 벌이 된다. **부하가 없는 프로젝트에서 얻는 것이
없다.** 권하지 않는다.

## 4. 권장

**안 A (TypeScript 단일)를 권한다.** 단, 아래 조건이면 안 B가 낫다.

### 안 A를 권하는 이유

1. **규칙 엔진 한 벌.** 이 프로젝트의 핵심 자산이 호환성 판정 로직이고(§2.2),
   그것이 두 벌로 갈리는 비용이 가장 크다
2. **§8의 SSR 요구가 스택 선택을 지배한다.** 검색 유입이 성장 경로인데, 그 요구를
   가장 직접적으로 푸는 생태계다
3. **견적 편집은 상태가 많은 UI다.** 부품 6종을 바꿔가며 즉시 판정을 보는 화면이고,
   §8A의 localStorage 연동까지 붙는다
4. Phase 2 Python 워커는 **DB로만 연결되는 배치**라(§7.2) 언어가 달라도 결합이 약하다

### 안 B가 나은 경우

- **Python에 익숙하고 TS에 익숙하지 않다.** 이 경우 안 A의 이점이 학습 비용에
  전부 상쇄된다. 스펙 §9의 "기존에 익숙한 것 우선"이 그래서 있다
- 어드민 구축 시간을 최소화하고 싶다 — Django admin이 거의 공짜다
- 서버 왕복 반응성을 감수할 수 있다

### 어느 쪽이든 공통

- **DB는 PostgreSQL.** `part_specs` key-value에 JSONB가 맞고, Phase 2 `price_history`
  시계열에도 무난하다 (스펙 §9). 이건 재론하지 않는다
- **캐시·큐는 넣지 않는다.** 부하가 없다 (§9)
- 규칙 엔진은 **DB·프레임워크에 의존하지 않는 순수 모듈**로 분리한다.
  스택을 바꾸더라도 이식되고, `pipeline-plan.md` §9.1 회귀 테스트의 중심이 된다
