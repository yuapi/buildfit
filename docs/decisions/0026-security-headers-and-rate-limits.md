# ADR-0026: CSP는 요청마다 nonce로, 요청 제한은 IP 단위 메모리 버킷으로

## 상태
채택 (2026-10-20, 이슈 #115)

## 배경

배포 전 보안 점검에서 다음이 나왔다.

- **보안 헤더가 하나도 없었다.** CSP·클릭재킹 방지·MIME 추측 방지가 없고 `X-Powered-By: Next.js`가 나갔다
- **서버 동작을 무제한 부를 수 있었다.** 검색·견적서 읽기는 DB 쿼리이고, 신고는 DB에 쓰고
  「검증 중」을 세운다. 브라우저 토큰은 클라이언트가 정하는 값이라 바꿔 가며 보내면 부품마다
  「검증 중」을 세울 수 있었다
- **어드민 비밀 대입이 무제한이었다.** 16자 이상이라 맞히기는 불가능하지만 시도 자체가 부하다

## 결정

### CSP — nonce, 모든 화면 동적 렌더링

Next 공식 방식대로 `proxy.ts`가 요청마다 nonce를 만들고 CSP에 넣는다. `script-src`에
`'unsafe-inline'`도 `'unsafe-eval'`(개발 모드 제외)도 없다. 외부 출처는 하나도 없다.

- **모든 화면이 동적 렌더링이다.** 정적으로 구운 화면에는 nonce가 없어 스크립트가 막힌다.
  레이아웃이 `headers()`로 nonce를 읽어 전부 동적으로 만든다 (`test/csp-nonce.test.ts`).
  원래 정적이던 것은 `/`와 `/calc/power` 둘뿐이고 나머지는 이미 `force-dynamic`이었다.
  sitemap·`robots.txt`는 HTML이 아니라 그대로 정적이다
- **스타일은 인라인을 허용한다.** React의 `style` 속성과 Next가 넣는 `<style>`이 있다.
  스타일 주입으로 할 수 있는 일은 스크립트보다 훨씬 좁다
- **외부 서비스를 붙이면 `lib/security-headers.ts`에 주소를 더한다**

탈락: 해시 기반 SRI(`experimental.sri`) — 실험 기능이고 Next의 인라인 데이터 스크립트를 덮지 못한다.
`'unsafe-inline'` — CSP가 XSS를 막지 못한다.

### 요청 제한 — IP 단위 토큰 버킷, 프로세스 메모리

캐시·큐를 두지 않는다 (ADR-0010). 서버는 한 대, 프로세스 하나다. 재시작하면 비지만 막으려는 것은
몰아치는 요청이지 장기 누적이 아니다.

| 대상 | 몰아 쓰기 | 다시 참 | 어디서 |
|---|---|---|---|
| 서버 동작 전체 | 120 | 초당 4 | `proxy.ts` — 검색이 글자마다 불리므로 넉넉히 |
| 신고 | 10 | 6분에 1 | 신고 동작 |
| 어드민 401 | 20 | 30초에 1 | `proxy.ts` — 막히면 비밀을 보기 전에 429 |

- **IP는 `X-Forwarded-For`의 맨 오른쪽 값이다.** 앱은 127.0.0.1에만 열고 Caddy가 앞에 선다.
  Caddy는 밖에서 온 값을 믿지 않고 실제 접속 IP로 채운다. 왼쪽 값은 지어낼 수 있다
- 기억하는 IP는 1만 개까지다. 주소를 바꿔 가며 메모리를 채울 수 없다

### proxy를 모든 화면에

공식 예시는 prefetch 요청을 matcher에서 빼라고 한다. **따르지 않는다** — `next-router-prefetch`
헤더 하나를 붙이면 어드민 검사를 건너뛴다 (화면·동작 쪽 `requireAdmin`이 한 번 더 막지만,
막는 곳이 둘인 이유가 사라진다 — ADR-0020).

## 결과

- 모든 HTML 응답이 요청마다 렌더링된다. 첫 화면도 DB를 부르지 않으므로 비용은 작다
- 여러 프로세스·여러 서버로 늘리면 요청 제한이 프로세스마다 따로 센다. 그때 다시 정한다
