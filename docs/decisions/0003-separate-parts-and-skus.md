# ADR-0003: parts(글로벌)와 skus(국내 유통)를 분리한다

## 상태
대체됨(ADR-0022) — 국내 유통 판정을 폐기했다. `skus`·`importers`는 스키마에서 지웠다

## 배경

1차 소스인 BuildCores OpenDB는 글로벌 부품 데이터베이스다 (ADR-0002). 그런데
**한국에서 못 사는 부품을 견적에 추천하면 도구로서 실패다.** (`pc-builder-spec.md` §5.7.1)

동시에 국내 유통에는 글로벌 스펙에 없는 층위가 있다.

- 같은 부품이 수입사(총판)별로 다른 상품으로 유통된다
  (`ASUS TUF GAMING B650-PLUS WIFI **대원CTS**`)
- 보증 정책은 부품이 아니라 **수입사마다** 정해진다
- 화면에 보여줄 이름은 영문 모델명이 아니라 국내 상품명이어야 한다
- 부품 표기가 제각각이다 — "RTX 4070 SUPER" / "지포스 RTX 4070 슈퍼" /
  "MSI 지포스 RTX 4070 SUPER 게이밍 X 슬림 D6X 12GB" (§5.2)

이 둘을 한 테이블에 합치면 호환성 판정과 구매 판단이 뒤섞인다.

## 결정

**부품을 두 층위로 나눈다.** (`pc-builder-spec.md` §5.8)

```
parts   글로벌 모델 — OpenDB에서 적재. 호환성 판정의 근거
skus    국내 유통 단위 — 네이버 쇼핑 매칭으로 생성. 구매 판단과 화면 표시
```

- **호환성 판정은 `parts`에서** 한다. 글로벌 스펙이 물리적 사실이기 때문이다
- **화면 표시와 구매 판단은 `skus`에서** 한다. `skus.display_name_ko`를 쓰고, 같은
  부품의 수입사별 옵션을 나란히 비교할 수 있다
- 보증 정책은 SKU마다가 아니라 **수입사마다** 두어 `warranty_policies`가
  `importers`에 걸린다. 수십 건 규모로 끝난다
- 표기 변형은 전부 `part_aliases`에 모으고, 부품마다 **canonical slug**를 하나씩 부여한다

```
slug 규칙: 소문자, 하이픈, 제조사-모델-변형
  예) amd-ryzen-7-7800x3d / nvidia-rtx-4070-super / msi-mag-b650-tomahawk-wifi
```

유통 판정은 §5.7.1의 7단계 매칭 파이프라인이 담당한다.

```
유효 SKU ≥ 1  →  국내 유통 (견적 선택 가능)
유효 SKU = 0  →  미유통 (선택 불가, 호환성 판정에는 여전히 사용)
```

## 이유

- **판정 근거와 구매 정보는 수명이 다르다.** 물리 치수는 바뀌지 않지만 유통 상태와
  가격은 주 단위로 바뀐다. 갱신 주기가 다른 데이터를 한 테이블에 두면 재조회가 전체를
  건드린다 (§5.7.1 갱신 주기)
- **미유통 부품을 지울 수 없다.** 업그레이드 진단(§6.5)에서 사용자의 기존 부품으로
  선택되어야 하고, 단종 이력 자체가 데이터로서 가치가 있다 (§5.6). 분리 구조라야
  "호환성 판정에는 쓰되 견적 선택지에서는 빼는" 처리가 자연스럽다
- **수입사별 옵션 비교가 가능해진다.** 같은 부품에 SKU가 여럿 달리므로, 보증 조건이
  다른 선택지를 나란히 보여줄 수 있다. 이건 §2에 없던 부가 차별점이다
- **`part_aliases`가 재사용된다.** §7 가격 정규화의 입력이자 검색 유입용 URL의 근거가
  같은 테이블에서 나온다

**검토한 대안**

| 대안 | 탈락 이유 |
|---|---|
| 단일 `parts` 테이블에 국내 필드 추가 | 수입사가 여럿이면 1:N이 성립하지 않는다. 보증 정책도 중복 저장된다 |
| 국내 유통 부품만 적재 | 업그레이드 진단에서 기존 부품(단종·미유통)을 선택할 수 없게 된다 |
| 미유통 부품 삭제 | 위와 같은 문제 + 단종 이력 소실 |

## 결과

**제약**

- 견적 결과 화면은 `skus`를 참조하지만 호환성 엔진은 `parts`를 참조한다. 두 경로가
  분리되므로 **SKU가 없는 부품도 견적 계산은 되어야 한다** (기존 부품 입력 경로)
- 유통 판정은 상태가 있는 값이다. `parts.kr_available` / `kr_checked_at`을 두고
  주기적으로 갱신한다. 이전에 SKU가 있었는데 연속 N회 조회에서 0이면 **단종 후보로
  플래그만 세우고 즉시 내리지 않는다** (§5.7.1)
- 총판 식별은 ML 없이 **총판명 사전 + 접미사 매칭**으로 한다. 미매칭은 검토 큐로 보내
  사전을 늘린다
- **이엠텍처럼 AIB 브랜드이면서 총판인 경우**가 있다. `parts.brand`와 `skus.importer_id`를
  혼동하지 않게 구분해야 한다
- 변형 토큰(WIFI 유무, DDR4/DDR5, 용량, OC 에디션) **완전 일치를 요구**한다. 놓치면
  다른 제품을 같은 것으로 묶는다
- 국내 유통 매칭 실패율 상승은 상품명 표기 변화로 자연 발생한다.
  `pipeline-plan.md` §10.2의 장애 지점이다

**후속 작업**

- `parts` / `part_specs` / `part_aliases` / `skus` / `importers` / `warranty_policies`
  스키마 확정 (§5.8 초안 기준)
- 국내 총판 사전 초안 작성 — 조사와 병렬 진행 가능한 단순 작업
- 네이버 쇼핑 API 앱 등록 및 쿼터 확인
- 매칭 파이프라인 7단계 구현, 검토 큐 포함
