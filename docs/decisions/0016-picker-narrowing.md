# ADR-0016: 고를 때 후보를 좁힌다 — 판정과 기준이 다르다

## 상태
채택 (2026-09-21)

## 배경

부품 고르기가 쓸모없을 만큼 시끄럽다. 실측값이다.

| 고른 것 | 고를 것 | 전체 | 맞는 것 |
|---|---|---:|---:|
| AM5 보드 | CPU | 789 | **45** |
| AM5 보드 | 메모리 (DDR5) | 4,876 | **2,701** |
| AM5 CPU | 메인보드 | 3,701 | **520** |
| Micro ATX 보드 | 케이스 | 3,782 | **3,397** |

AM5 보드를 고른 사람에게 LGA1151 CPU 744개를 보여주고 있었다.
검색은 **이름 부분 일치**만 했고, 정렬만 출시연도 역순이었다.

### 원래 계획은 이게 아니었다

명세 §5.7.1은 국내 유통 매칭(`skus`)으로 목록을 좁힐 생각이었다.
그런데 그 길이 막혔다.

- **네이버 API 약관에 결과 저장·DB화 금지 조항이 있다** (이슈 #8).
  `skus` 저장 설계와 부딪힌다. 이 환경에서 원문을 못 읽어 확인이 남았다
- OpenDB `retailer_listings`에 **한국 채널이 0건**이다 (전수 확인).
  미국 28,764 · 영국 28,673 · 일본 10,195건인데 한국은 없다
- `parts.kr_available`은 22,962건 전부 비어 있다

즉 **유통 데이터를 기다리면 이 문제는 안 풀린다.** 그런데 문제의 본질은
유통이 아니었다. 사용자가 겪는 것은 "안 맞는 부품이 섞여 나온다"이고,
그건 **우리가 이미 가진 데이터로 푼다.**

## 결정

**이미 고른 부품에서 제약을 유도해 후보를 좁힌다.**

### 1. ★ 좁히기는 판정이 아니다. 결측을 반대로 다룬다

| | 판정 (규칙 엔진) | 좁히기 (고르기) |
|---|---|---|
| 값이 없으면 | `unknown`. 통과시키지 않는다 (ADR-0009) | **남긴다** |
| 근거 | 거짓 통과가 최악의 결과다 | 숨기면 그 부품을 **찾을 방법이 없다** |

그래서 모든 제약을 "**아는데 어긋나는 것만 뺀다**"로 쓴다. SQL로는 전부
`not exists (… 어긋나는 스펙 …)`이다. `exists (… 맞는 스펙 …)`으로 뒤집으면
스펙이 비어 있다는 이유로 멀쩡한 부품이 사라진다.

실제로 이 차이가 크다. 소켓 스펙이 없는 메인보드 4건은 AM5 필터에서
살아남아야 하고, 살아남는다 (516 + 4 = 520).

### 2. ★ 오류를 내는 규칙에서만 제약을 유도한다

규칙 1(소켓)·2(메모리 규격)·4(GPU 길이)·5(보드 폼팩터)·6(파워 규격)에서 유도한다.
각 제약에 `ruleId`와 `because`를 달아 **어느 규칙에서 왔고 무엇 때문인지**
화면이 말할 수 있게 한다.

**규칙 9(쿨러 높이)는 쓰지 않는다.** 경고까지만 내고 오류 경계가 없기 때문이다.
그 규칙 자신이 이유를 적어뒀다 — "제조사의 최대 높이는 보수성이 제각각이고,
팬 위치를 옮겨 들어가는 사례가 실재한다. **오류로 단정하면 쓸 수 있는 조합을
막는다**" (§9.1). 목록에서 빼는 것은 단정보다 강하다. 사용자가 경고를 볼
기회조차 없어진다.

규칙 4도 **오류 경계만** 쓴다. 빠듯함 경고 구간(95%)으로는 빼지 않는다.

> **검토에서 잡힌 것.** 처음 구현은 규칙 9로 쿨러를 좁혔다. 한계가 45mm인
> 케이스(NZXT H1 등, AIO를 끼워 파는 SFF)를 고르면 **`height_mm`가 있는 수랭
> 쿨러 559개 중 529개가 사라졌다.** 저장된 값이 라디에이터 높이라 그렇다.
> AIO가 필요한 바로 그 사용자가 AIO를 못 찾았다. 규칙 9는 그 조합을 한 번도
> 실패로 판정하지 않는데 화면이 지워버린 것이다.

방향이 양쪽이다. CPU를 고르면 보드가 좁혀지고, 보드를 고르면 CPU가 좁혀진다.
GPU를 고르면 케이스의 `max_gpu_length_mm` **하한**이 생긴다.

### 3. 규칙이 단정하지 않는 것은 여기서도 단정하지 않는다

- 칩만 고른 GPU는 길이를 모르므로 케이스를 좁히지 않는다 (규칙 4의 `chipOnly`)
- 쿨러는 어느 방향으로도 좁히지 않는다 (위 §2)

### 4. 끌 수 있고, 몇 개를 왜 숨겼는지 말한다

기본은 켜짐이다. 「맞는 것만 보기」를 끄면 전체가 나온다.
숨긴 건수와 이유를 함께 적는다 — 목록이 짧은 이유를 말하지 않으면
사용자는 부품이 없는 줄 안다.

### 5. 코드는 규칙 엔진과 따로 두되 출처를 남긴다

규칙은 `Build`(고른 부품들)를 받고, 좁히기는 **아직 고르지 않은 후보**를
상대하므로 입력이 다르다. 한 함수로 합치면 둘 다 어색해진다.
대신 `ruleId`로 출처를 달아, 둘이 어긋나면 테스트가 잡게 한다.

## 이유

### 왜 유통 매칭을 기다리지 않는가

기다릴 근거가 없다. 네이버 약관 확인은 사용자 작업이고(이슈 #8), 확인 결과가
나빠도 이 개선은 그대로 유효하다. **의존을 끊는 쪽이 맞다.**

### 검토한 대안

| 대안 | 탈락 이유 |
|---|---|
| 국내 유통 매칭으로 좁힌다 | 막혔고(이슈 #1·#8), 막히지 않았어도 "안 맞는 부품" 문제는 그대로다 |
| 현행 세대만 보여주기 (출시연도·소켓 화이트리스트) | 세대 목록을 손으로 관리해야 하고, 구형 업그레이드 사용자를 막는다 |
| 안 맞는 것을 **표시만** 하고 목록엔 남긴다 | 744개 중 45개를 찾는 문제는 그대로다. 다만 이 방식을 토글로 제공한다 |
| 결측도 숨긴다 | **하면 안 된다.** 스펙이 빈 부품을 찾을 방법이 사라진다. 이 프로젝트에서 데이터가 없는 것은 흔한 상태다 |
| 「검증 중」인 값으로도 숨긴다 | **하면 안 된다** (이슈 #14). 다투어지는 값은 아는 값이 아니다 — 결측·단위 오류와 같은 자리다 |

## 결과

- 새 규칙을 만들면 **좁히기 제약도 같이 볼 것.** 판정만 하고 목록을 안 좁히면
  사용자는 안 맞는 걸 고른 뒤에야 안다
- 제약을 추가할 때 **두 가지를 먼저 확인한다.**
  1. 그 규칙이 **오류를 내는가.** 경고까지만 내는 규칙으로 목록을 빼면
     "확인이 필요하다"가 "없다"로 바뀐다. 테스트가 `ruleId`를 검사한다
  2. **방향이 맞는가.** "아는데 어긋나는 것만 뺀다"를 어기면 조용히 부품이 사라진다
- **「검증 중」(`part_specs.disputed`)인 행으로는 숨기지 않는다** (이슈 #14).
  판정이 틀리면 사용자가 그 부품을 보고 의심할 수 있지만(ADR-0021이 「검증 중인
  값으로 판정했습니다」라고 적는다), 거르기가 숨기면 **찾을 길이 없다.**
  실측: XFX Quicksilver RX 9070 XT는 한 기록이 360mm, 쌍둥이 기록이 350mm다.
  355mm 케이스를 고르면 그 제품이 목록에서 통째로 사라지고 있었다
- SQL이 그 선의 **유일한 강제 지점**이다. `'null'::jsonb #>> '{}'`는 SQL NULL이고
  `NULL is distinct from 'AM5'`는 참이라, 타입 가드가 없으면 값이 없는 행이
  "어긋남"으로 잡힌다. 빈 문자열·빈 배열·타입 불일치도 같다.
  지금 데이터에는 그런 행이 없지만(196,854행 전수 확인) 스키마가 허용한다.
  테스트가 다섯 종류 모두와 나쁜 값들을 고정한다 (`apps/ingest/test/picker-sql.test.ts`)
- 검색 요청은 **번호를 공유한다.** 짧은 접두사일수록 느리다 — 숨긴 건수를 세느라
  이름이 걸린 집합 전체를 훑는다 (실측 13ms vs 2.3ms). 순서 보장이 없으면
  "ryzen 7 9800"을 빨리 칠 때 'r'의 결과가 나중에 도착해 화면을 덮는다.
  타이핑 경로와 토글 경로가 같은 번호를 써야 마지막 요청이 이긴다
- 클라이언트가 보낸 제약은 서버에서 모양을 확인한다. 값은 전부 파라미터로
  들어가지만 모양이 어긋나면 쿼리가 던져 검색이 통째로 죽는다.
  이상한 것은 조용히 버린다 — 좁히기가 덜 되는 것이 검색이 죽는 것보다 낫다
- 숨긴 건수를 세느라 쿼리가 두 벌 돈다. 22,962건 규모에서는 문제없지만
  카탈로그가 더 커지면 다시 본다
