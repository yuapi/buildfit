# ADR-0027: 같은 서버에 3200으로, 서버가 main을 당겨 배포한다

## 상태
채택 (2026-10-20, 이슈 #117)

## 배경

배포할 서버에 이미 다른 서비스 둘이 돈다 — 3000·3100을 쓰고, 앞에 Caddy 하나가 도메인별로 나눈다.
`docs/oci-migration.md`는 빈 OCI 인스턴스를 가정해 3000을 썼다.

같은 서버의 다른 서비스는 서버에 GitHub Actions 자체 러너를 두고 main 머지 때 배포한다.
**이 레포는 public이다.** public 레포의 자체 러너는 포크 PR이 워크플로를 고쳐 서버에서 코드를 돌릴 수 있다
(GitHub 문서도 권하지 않는다). GitHub 서버의 러너가 SSH로 들어오게 하려면 22번을 밖에 열고 키를 시크릿에 둬야 한다.

## 결정

- **127.0.0.1:3200**, Caddy가 앞단. 실행 계정 `buildfit`, 서비스 DB는 같은 서버의 PostgreSQL 16(일반 역할)
- **서버가 당긴다.** systemd 타이머가 2분마다 `origin/main`을 보고, 바뀌었으면 `deploy/deploy.sh`가 배포한다.
  들어오는 접속도, GitHub 시크릿도, 러너도 없다. main 머지에서 배포까지 길어야 2분 남짓 + 빌드 시간
- **릴리스 폴더.** 새 폴더에 꺼내 `npm ci`·마이그레이션·빌드를 하고, 끝나면 `current` 링크를 바꿔 재시작한다.
  빌드하는 동안 서비스는 옛 폴더에서 돈다. 헬스 체크(`/healthz`)에 실패하면 이전 폴더로 되돌린다.
  실패한 커밋은 기록해 두고 타이머가 다시 빌드하지 않는다 — 새 커밋이 오거나 손으로 돌릴 때만
- 마이그레이션은 전환 **전에** 돈다 (deployment.md §6 — 컬럼 추가는 옛 버전과 공존한다)
- 주간 OpenDB 재동기(새 커밋이 있으면 재적재 + 재빌드), 매일 `pg_dump` 14개

## 결과

- 배포 상태는 GitHub Actions 화면이 아니라 서버의 `journalctl -u buildfit-deploy`에 있다
- 마이그레이션이 옛 버전과 공존하지 못하는 변경(컬럼 삭제·이름 변경)은 되돌리기가 DB까지 되돌리지 않는다.
  expand-contract를 지킨다 (pipeline-plan §7.1)
