# ADR-0008: Git Flow 브랜치 전략을 따른다

## 상태
채택. **머지 방법은 ADR-0024가 대체한다** (2026-09-24) — PR로 머지하고, `merge` 방식이 `--no-ff`를
대신하며, 머지된 feature 브랜치는 워크플로가 지운다. 브랜치 구조와 이름은 그대로다.

## 배경

레포에 브랜치 규칙이 없었다. 초기 구성 커밋이 세션 브랜치에 올라갔고, `main`은 그
커밋에서 뒤늦게 만들어졌으며, 기본 브랜치는 세션 브랜치를 가리킨 채였다. 브랜치 두
개가 같은 커밋을 가리키면서 **무엇이 "배포된 상태"인지 가리키는 것이 아무것도 없는**
상태다.

이 프로젝트에서는 그게 단순한 정리 문제가 아니다. `pipeline-plan.md`가 전제하는
자율 운영은 브랜치 의미가 고정되어 있어야 성립한다.

- §8A.1 — FROZEN 진입 시 **freeze point(그 시점의 배포된 커밋 SHA)** 를 고정해야 한다
- §5.2 — CD 프리플라이트가 `$PREV..$HEAD` 범위의 전 커밋 출처를 검증한다.
  이 범위가 무엇인지 정의되려면 배포 브랜치가 하나여야 한다
- §8A.2 — FROZEN 해제 시 "freeze point 이후 쌓인 변경"을 전수 조사한다.
  **쌓일 자리**가 필요하다

또 하나. 세션이 이슈 단위로 끊어 돌아가는 구조(`handoff-guide.md` §6)라서, 작업
단위와 브랜치 단위가 일치하지 않으면 다음 세션이 어디서부터 이어받을지 알 수 없다.

## 결정

**Git Flow를 따른다.**

| 브랜치 | 용도 | 분기 원본 | 머지 대상 |
|---|---|---|---|
| `main` | **배포된 것만.** 릴리스마다 태그 | — | — |
| `develop` | 통합 브랜치. **레포 기본 브랜치** | `main` | — |
| `feature/<이슈번호>-<요약>` | 기능·문서·데이터 작업 | `develop` | `develop` |
| `release/<버전>` | 릴리스 준비 (버그 수정만) | `develop` | `main` + `develop` |
| `hotfix/<요약>` | 배포된 것의 긴급 수정 | `main` | `main` + `develop` |

**규칙**

- **`main`과 `develop`에 직접 커밋하지 않는다.** 항상 브랜치를 따서 머지한다
- 머지는 **`--no-ff`**. 작업 단위가 히스토리에 남아야 한다
- **이슈 하나 = feature 브랜치 하나.** 여러 이슈를 한 브랜치에서 처리하지 않는다
  (`handoff-guide.md` §6: 긴 작업은 이슈 단위로 끊는다)
- 머지한 feature 브랜치는 삭제한다
- 이슈 번호가 없는 작업은 `feature/<요약>`

**버전과 릴리스**

- 릴리스 태그는 **semver**. 1.0 이전이므로 **Phase 완료마다 minor를 올린다**
  - Phase 0a 완료 → `v0.1.0`, Phase 0b 완료 → `v0.2.0`, …
- 릴리스 브랜치 이름은 버전을 쓴다 — `release/0.1.0`
- `v1.0.0` 승격은 semver major 상승이므로 `pipeline-plan.md` §3.1에 따라 **T2(승인 필수)** 다

## 이유

- **"배포된 것"이 `main` 하나로 정의된다.** freeze point가 `main`의 tip으로 확정되고,
  CD 프리플라이트의 검증 범위도 `main`의 이전 tip부터로 명확해진다. 이게 이 전략을
  택한 가장 큰 이유다
- **미배포 변경이 쌓일 자리가 생긴다.** §8A가 다루는 "FROZEN 중 쌓인 변경 재조정"은
  쌓이는 브랜치가 있어야 성립한다. `develop`이 그 자리다
- **릴리스 단위가 이미 있다.** 로드맵의 Phase(`pc-builder-spec.md` §11)가 그대로
  릴리스 단위다. "각 Phase가 곧 배포 단위이자 파이프라인 검증 대상"이라고 스펙이
  명시하고 있어, release 브랜치와 1:1로 맞는다
- **머지 지점이 곧 승인 지점이다.** `release`/`hotfix` → `main` 머지가 T2 승인
  경로(§4)와 자연스럽게 겹친다. 승인받을 대상이 브랜치 하나로 떨어진다
- **`--no-ff`가 작업 단위를 보존한다.** 커밋을 작게 쪼개는 규칙(CLAUDE.md 작업 규칙 5)과
  합쳐지면, 머지 커밋이 이슈 경계가 되고 그 안이 세부 변경이 된다. 다음 세션이
  히스토리만 보고 작업 단위를 복원할 수 있다

**검토한 대안**

| 대안 | 탈락 이유 |
|---|---|
| GitHub Flow (`main` + feature) | 단순하지만 "배포된 것"과 "통합된 것"이 같아진다. 미배포 변경이 쌓일 자리가 없어 §8A 재조정 절차가 성립하지 않는다 |
| Trunk-based | 자동 배포와 가장 잘 맞지만 **feature flag 인프라가 전제**다. 지금은 없고, `pipeline-plan.md` §10.3의 기능 단위 flag는 Phase 2 이후 이야기다 |
| 브랜치 전략 없이 진행 | 지금 상태. 무엇이 배포된 것인지 정의되지 않아 파이프라인 구축 자체가 막힌다 |

## 결과

**제약**

- **Renovate의 `baseBranches`를 `develop`으로 지정해야 한다.** `pipeline-plan.md`
  §14.2 초안의 `automergeType: "branch"`는 기본값이면 기본 브랜치를 직접 머지 대상으로
  삼는다. 지정하지 않으면 의존성 업데이트가 `main`에 바로 들어가 Git Flow가 깨진다.
  **이 설정을 빠뜨리면 전략이 조용히 무너지므로 파이프라인 구축 시 최우선 확인 항목이다**
- **release 브랜치는 자동 배포와 마찰이 있다.** §3.2는 T0를 "무승인, PR 없음, 즉시
  진행"으로 두고 §9.4는 blue-green 즉시 전환인데, Git Flow는 release 브랜치라는
  단계를 끼워 넣는다. **Phase 단위 릴리스가 드물어서 지금은 감당 가능하지만, 배포
  빈도가 올라가면 재검토 대상이다.** 그때는 hotfix 경로를 T0의 기본 통로로 넓히거나
  trunk-based로 옮기는 선택지가 있다
- **머지 커밋도 봇 서명이 필요하다.** §5.2 프리플라이트는 배포 범위 내 전 커밋을
  검증하므로 `--no-ff` 머지 커밋도 서명 대상이고 `X-Pipeline-Run` trailer가 붙어야 한다
- 브랜치가 늘어나는 만큼 정리를 안 하면 지저분해진다. 머지 후 삭제를 규칙으로 둔다

- [ ] `main` 브랜치 보호 규칙 — force-push 금지, 관리자 포함
      (`pipeline-plan.md` §5.3) *(레포 설정 — 수동)*
- [ ] 초기 구성 세션 브랜치 `claude/buildfit-initial-setup-23acp8` 삭제
      (`main`에 머지 완료됨)
- [ ] 파이프라인 구축 시 Renovate `baseBranches: ["develop"]` 설정
