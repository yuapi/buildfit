# ADR-0009: 데이터가 없으면 "판정 불가"로 표시한다 (결측을 통과로 처리하지 않는다)

## 상태
채택

## 배경

OpenDB 스키마 조사(`docs/research/opendb-schema-analysis.md`)에서 구체적인 숫자가
나왔다. §4.1 필수 규칙 8개 중 7개는 1차 소스만으로 판정 가능하지만, **규칙 6(PSU
폼팩터 ⊂ 케이스 지원)에 필요한 케이스 필드가 현행 세대에서도 83.2% 결측**이다
(3,396건 중 2,827건).

Phase 1로 가면 더 넓어진다.

| 규칙 | 결측 |
|---|---|
| 6 — PSU 폼팩터 | 케이스 83.2% |
| 9 — 쿨러 높이 | 케이스 64.2%, 쿨러 29.6% |
| 10 — 라디에이터 | 케이스 **필드 자체 부재** |
| 11 — 메모리 높이 | DDR5 74.8% |
| 12 — BIOS | 보드 출시연도 40.1% |

즉 **결측은 예외가 아니라 정상 상태**다. 그렇다면 규칙 엔진이 "필요한 값이 없을 때
무엇을 반환하는가"는 구현 세부사항이 아니라 제품 설계 결정이다.

가장 쉬운 구현은 결측 시 그 규칙을 건너뛰고 통과로 처리하는 것이다. **그러면 사용자는
"호환성 확인 완료"를 보고 케이스에 안 들어가는 파워를 산다.**

## 결정

**§4.3 판정 등급에 "판정 불가"를 추가한다.** 기존 오류/경고/정보에 이어 네 번째 등급이다.

- 규칙이 필요로 하는 필드가 **하나라도 비어 있으면 그 규칙은 판정 불가**다.
  통과도 실패도 아니다
- **어느 부품의 어느 항목이 없어서 판정하지 못했는지 명시한다.** "확인 불가"만 띄우지
  않는다
- 결과 요약에서 **"모든 검사 통과"라고 쓰지 않는다.** 통과 n건 / 판정 불가 m건으로 나눈다
- 판정 불가 항목은 §5.5의 빈 필드 보강 큐로 연결한다. 사용자가 마주친 결측이 곧
  보강 우선순위 신호다
- 회귀 테스트에 **필요 필드를 비운 부품으로 "판정 불가"가 나오는지** 검증하는 케이스를
  넣는다 (§10.4). 결측이 조용히 통과로 바뀌는 회귀가 가장 위험하다

## 이유

- **이 도구의 최악의 실패 모드는 틀린 "통과"다.** 스펙 §5.3이 "스펙 오류는 사용자가
  실제로 부품을 잘못 사게 만드는 결과로 이어진다"고 적은 그대로다. 수십만 원짜리
  결정이고, 되돌리려면 반품·재구매를 해야 한다
- **모르는 것을 모른다고 하는 것이 이 프로젝트의 기존 원칙이다.** CLAUDE.md의
  "근거 없는 수치를 지어내지 않는다. 데이터가 없으면 없다고 표시한다", ADR-0004의
  예측 구간 표시, §6.6.4의 "추정 불가 시 수치를 내지 않는다"와 같은 계열이다.
  호환성 판정만 예외로 둘 이유가 없다
- **선례가 파이프라인에 이미 있다.** `autonomous-pipeline-plan.md` §9.6은 관측 표본이
  부족하면 "이상 없음"이 아니라 "판정 불가"로 처리하고 합성 트래픽을 추가 주입하라고
  한다. 같은 원칙을 제품 쪽에 적용하는 것이다
- **결측을 드러내면 보강 우선순위가 공짜로 얻어진다.** 사용자가 실제로 고른 조합에서
  판정 불가가 뜬 필드가 곧 가장 값진 보강 대상이다. §5.5의 "사용자 제보가 가장 값싼
  검증 수단"과 같은 메커니즘이다
- **신뢰가 이 도구의 유일한 자산이다.** 가격도 커머스도 없으므로(ADR-0006) 사용자가
  다시 오는 이유는 판정을 믿을 수 있어서다. 한 번 틀린 "통과"가 그것을 깎는다

**검토한 대안**

| 대안 | 탈락 이유 |
|---|---|
| 결측 시 통과 처리 | 위 전부. 가장 쉽고 가장 위험하다 |
| 결측 시 오류 처리 | 안전하지만 83% 결측 상황에서 멀쩡한 조합이 전부 빨간불이 된다. 경보 피로로 사용자가 판정 전체를 무시하게 된다 |
| 결측 시 경고 처리 | 판정 불가와 혼동된다. "간섭 가능성 있음"(실제 리스크)과 "데이터 없음"(우리 문제)은 사용자가 할 행동이 다르다 |
| 필드가 채워진 부품만 선택지에 노출 | 케이스 83%가 사라진다. 선택지 자체가 무너진다 |

## 결과

**제약**

- **결과 화면이 4가지 상태를 표현해야 한다.** 오류/경고/정보/판정 불가. UI에서
  판정 불가가 경고처럼 보이면 안 된다. 색과 아이콘을 구분한다
- 규칙 엔진의 반환 타입이 boolean이 아니다. `pass | fail | unknown` 3값을 가지며,
  `unknown`에는 **어느 필드가 없었는지**가 실려야 한다
- `compat_rules` / `build_checks` 스키마(§5.8)가 이 3값을 저장할 수 있어야 한다.
  `build_checks.result`를 boolean으로 두지 않는다
- **Phase 0 초기에는 판정 불가가 흔하게 뜬다.** 케이스 보강 전에는 규칙 6이 대부분
  판정 불가다. 이것이 사용자에게 "덜 만들어진 도구"로 보일 위험이 있으므로,
  문구로 "데이터를 채우는 중"임을 드러내고 보강 진행 상황을 신호로 삼는다
- 합성 트래픽 시나리오(§10.1)에 판정 불가 경로를 추가해야 한다

**후속 작업**

- [ ] 규칙 엔진 반환 타입 설계 — `unknown` + 결측 필드 목록
- [ ] `build_checks.result` 3값 저장 (§5.8 스키마 확정 시)
- [ ] 판정 불가 UI 표현 확정 (색·아이콘·문구)
- [ ] 회귀 테스트: 필드를 비운 부품으로 각 규칙이 판정 불가를 내는지 (§10.4)
- [ ] 판정 불가 → 빈 필드 보강 큐 연결 (§5.5)
