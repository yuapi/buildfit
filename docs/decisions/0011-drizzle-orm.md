# ADR-0011: DB 접근 계층은 Drizzle ORM을 쓴다

## 상태
채택

## 배경

ADR-0010으로 PostgreSQL + TypeScript가 정해졌고, 이슈 #3(OpenDB 적재)을 시작하려면
스키마를 코드로 표현할 방법이 필요하다.

이 프로젝트의 DB 사용에는 세 가지 특성이 있다.

1. **`part_specs`가 key-value다** (§5.8). 카테고리마다 스펙 항목이 완전히 달라
   컬럼으로 고정할 수 없다. JSONB 쿼리가 일상적으로 필요하다
2. **Phase 2에 Python 워커가 같은 DB를 읽는다** (ADR-0010). 경계를 DB로만 한정했으므로
   스키마가 언어 중립적으로 읽혀야 한다
3. **마이그레이션 위험도를 기계적으로 판정해야 한다.** `pipeline-plan.md` §3.1은
   `DROP`·`ALTER COLUMN`·NOT NULL 추가를 T2(승인 필수)로, add-only를 T0로 분류한다.
   §7은 자가수복이 expand만 수행하도록 강제한다

3번이 특히 중요하다. **분류기가 판정할 대상은 생성된 SQL이다.** SQL이 보이지 않으면
위험도를 판정할 수 없고, 그러면 파이프라인의 리스크 분류(§3)가 이 레포에서 작동하지
않는다.

## 결정

**Drizzle ORM을 쓴다.** 마이그레이션은 SQL 파일로 생성해 레포에 커밋한다.

## 이유

- **생성되는 SQL이 투명하다.** 마이그레이션이 사람이 읽는 `.sql` 파일로 나오므로,
  `pipeline-plan.md` §3의 리스크 분류기가 `DROP`·`ALTER COLUMN` 같은 패턴을
  **텍스트로 검사**할 수 있다. expand/contract 판정(§7.1)도 마찬가지다
- **JSONB를 제약 없이 다룬다.** `part_specs`의 key-value와 Phase 2 `price_history`
  시계열 모두 PostgreSQL 기능을 그대로 쓸 수 있다
- **런타임 의존이 얇다.** 쿼리 빌더에 가까워 번들과 콜드스타트에 부담이 적다.
  Next.js 서버 컴포넌트에서 직접 쓰기 좋다
- **스키마가 언어 중립적으로 남는다.** 진실 소스가 SQL 마이그레이션이므로 Python
  워커가 ORM 메타데이터를 해석할 필요가 없다

**검토한 대안**

| 대안 | 탈락 이유 |
|---|---|
| Prisma | 생태계와 문서는 가장 두껍다. 하지만 **생성 SQL이 불투명해 마이그레이션 위험도(T0/T2) 판정이 어렵고**, JSONB 쿼리가 제한적이다. 자체 엔진 바이너리도 배포 단위를 무겁게 한다 |
| raw SQL + Kysely | 통제력은 최고지만 스키마 변경·마이그레이션을 전부 손으로 관리해야 한다. 개인 프로젝트에서 그 비용이 얻는 것보다 크다 |
| TypeORM / Sequelize | 데코레이터·액티브레코드 계열은 마이그레이션 투명성이 더 낮다 |

## 결과

**제약**

- **마이그레이션 SQL을 반드시 커밋한다.** 런타임 자동 생성(push)에 의존하지 않는다.
  커밋된 SQL이 리스크 분류의 입력이다
- **`drizzle-kit push`는 개발 편의용으로도 쓰지 않는다.** 스키마 변경이 SQL 파일로
  남지 않으면 §7의 expand-contract 강제가 무너진다
- 자가수복 루프가 만질 수 있는 것은 **add-only 마이그레이션뿐**이다
  (`pipeline-plan.md` §7.1). contract는 별도 예약 작업으로 큐잉한다
- Python 워커는 Drizzle을 쓰지 않는다. **스키마를 SQL로 읽고 직접 접근**한다.
  ORM을 양쪽에 두지 않는다
