# ADR-0002: BuildCores OpenDB를 1차 데이터 소스로 한다

## 상태
채택

## 배경

이 프로젝트의 진짜 관문은 로직이 아니라 데이터다. 호환성 판정은 소켓·폼팩터·물리 치수·
커넥터 구성 같은 정확한 스펙이 있어야 성립하는데, 수집 난이도가 카테고리마다 다르고
메인보드·GPU는 특히 어렵다. (`pc-builder-spec.md` §5.1)

**"로직은 며칠이면 짜지만 데이터는 계속 일이다. 여기서 포기하지 않는 것이 성패를 가른다."**

따라서 초기 적재를 어디서 시작하느냐가 프로젝트 지속 가능성을 결정한다. 전량 수동
입력으로 시작하면 부품 100개를 채우다 지친다. (§5.3)

## 결정

**BuildCores OpenDB를 1차 데이터 소스로 확정한다.** (`pc-builder-spec.md` §5.7)

```
저장소  github.com/buildcores/buildcores-open-db
구조    /open-db/<CATEGORY>/<uuid>.json   부품 1개 = 파일 1개
        /schemas/                          카테고리별 JSON 스키마
수집    git clone → 갱신은 git pull (주 1회)
라이선스 ODC-By 1.0 — 출처 표기가 유일한 조건
```

보조 소스의 역할은 다음과 같이 한정한다.

| 소스 | 역할 |
|---|---|
| 네이버 쇼핑 API | 국내 유통 판정 + SKU + 가격 (OpenDB가 다루지 않는 영역) |
| 제조사 스펙시트 | 빈 필드 보강, 검증 |
| GS1 코리안넷 | GTIN 매칭 보조. 기대치 낮음 |
| Icecat (Open) | OpenDB 커버리지 부족 시에만 |
| PCPartPicker | **배제** |

## 이유

- **용도가 정확히 일치한다.** OpenDB README가 호환성 검사와 PC 빌더 앱 제작 용도를
  명시하고 있다
- **라이선스가 깨끗하다.** ODC-By 1.0은 복사·배포·2차 저작물·수정을 모두 허용하고
  조건은 출처 표기뿐이다. 검증된 값을 우리 DB에 저장하는 §5.7.3 원칙에 제약이 없다
- **API도 쿼터도 없다.** git clone 한 번으로 초기 적재가 끝나고, 갱신은 git pull이다.
  외부 API 의존이 없으므로 쿼터 초과나 약관 변경 리스크가 없다
- **수집 비용을 커뮤니티와 분담한다.** fork로 두고 주기적 sync하면, 프로젝트가 방치되어도
  우리 fork에 데이터가 남는다. 국내 유통 데이터와 스펙 정정을 업스트림에 PR할 여지도 있다

**검토한 대안**

| 대안 | 탈락 이유 |
|---|---|
| PCPartPicker 스크래핑 | 공식 API 없고 공개 계획도 없다. 비공식 스크래퍼는 ToS 위반이고 차단당한다 |
| Icecat을 1차로 | 무료 등급이 브랜드 스폰서 제품만 덮고, 모든 제품 페이지에 "Specs Icecat" 표기·링크·AS IS 면책조항이 요구된다. 커버리지도 표기 부담도 불리 |
| 전량 수동 입력 | 지친다. §5.3이 반자동을 택한 이유 그대로다 |
| 전량 자동 수집 | 정확도가 안 나온다. 스펙 오류는 사용자가 부품을 잘못 사게 만든다 |

## 결과

**제약**

- **가격과 리테일러 데이터는 OpenDB가 제공하지 않는다** (명시적 제약). 가격은 네이버
  쇼핑 API로 별도 처리해야 한다
- **리테일러 커버리지가 미국 중심이다.** 국내 유통 판정이 별도 파이프라인으로 필요하다
  → ADR-0003
- **메인보드 BIOS 버전별 CPU 지원 목록은 OpenDB에도 없다.** 수집 목표로 등재되어 있으나
  미완이다. §4.2의 난제가 여기서도 미해결이므로, Phase 0에서는 출시일 비교 기반 경고만
  낸다 (§5.1 메인보드 대응 전략)
- **출처 표기 영역을 설계에 미리 포함해야 한다.** 페이지 하단과 부품 상세에 ODC-By
  표기 자리를 둔다
- 업스트림 스키마 변경이 곧 적재 실패로 이어진다. `pipeline-plan.md` §10.2의
  "자연 발생 장애" 지점이다

**후속 작업 (Phase 0a)**

- clone 직후 5분 확인 (§5.7) — 이 셋이 §2.2 차별점의 실현 가능성을 가른다
  - 케이스 스키마에 GPU 최대 길이 / 쿨러 최대 높이 / 라디에이터 장착 필드가 있는가
  - GPU 스키마에 AIB 모델별 물리 치수가 있는가
  - 현행 세대 커버리지 — 국내 인기 부품 20개를 찾아본다
- §4.1 호환성 규칙 8개 각각에 필요한 필드의 OpenDB 존재 여부 대조표 작성
- 없는 필드는 §5.3 반자동 워크플로(어드민)로 보강. 보강 규모를 먼저 추정한다
- fork 생성 및 sync 주기 설정
