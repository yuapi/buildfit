# ADR-0017: 한국어로 검색한다 — 사전은 코드에, 평탄화는 생성 컬럼에

## 상태
채택 (2026-09-21)

## 배경

검색이 한국 사용자에게 **전부 빗나가고 있었다.** 실측이다.

| 검색어 | 결과 |
|---|---:|
| 라이젠 | **0** |
| 지포스 5080 | **0** |
| 삼성 | **0** |
| 에이수스 | **0** |
| `rtx 4070` | 269 |
| `rtx4070` | **0** |

조건은 `model_name ilike '%q%'` 하나였다. 카탈로그(BuildCores OpenDB)는 전부
영문인데 사용자는 한국어를 친다. 게다가 **띄어쓰기 한 칸이 269건과 0건을 갈랐다.**

상세와 원인은 `docs/research/korean-search-terms.md`.

### 이게 왜 이 도구에서 특히 아픈가

이 도구는 판단을 돕는다. 판단하려면 먼저 **부품을 고를 수 있어야** 한다.
ADR-0016으로 안 맞는 후보를 걸러내 목록을 744개에서 45개로 줄여놨는데,
그 45개를 **찾을 말이 없으면** 아무 소용이 없다.

## 결정

세 가지를 한다.

### 1. ★ 한글 표기를 영문으로 바꾼다. 사전은 코드에 둔다

`packages/compat/src/search.ts`의 `KO_ALIASES`가 `라이젠 → ryzen`을 한다.

**DB 테이블이 아니라 코드에 두는 이유**는 이것이 데이터가 아니라 결정이기
때문이다. 어떤 말을 받아들일지는 리뷰를 거쳐야 하고, 되돌릴 수 있어야 하고,
테스트가 걸려야 한다. `part_aliases` 테이블은 이미 있지만 그건 **부품마다 붙는
표기 변형**(모델명·파트넘버)이고, 여기서 필요한 것은 부품과 무관한 **말의 사전**이다.

넣을 말은 **카탈로그에 실제로 걸리는지 세어보고** 고른다 (조사 §5).
「티아이」(Ti)는 그래서 뺐다 — 구분자를 지우면 `ti`가 `Edition` 안에도 있어서
실측 151건 중 74건이 4070 Ti가 아니었다. 사전 항목의 영문은 **3글자 이상**이어야
하고 테스트가 그 경계를 지킨다.

### 2. ★ 양쪽에서 구분자를 지우고 맞댄다. 카탈로그 쪽은 생성 컬럼으로

`squash()`는 영문 소문자와 숫자만 남긴다. `rtx 4070`과 `rtx4070`과 `rtx-4070`이
같은 모양이 된다.

카탈로그 쪽은 `parts.search_text` **생성 컬럼**이 같은 일을 한다.
`model_name + brand + mpn`을 이어 붙여 눌러둔다.

- **브랜드**를 넣는 이유: 이름이 브랜드로 시작하지 않는 부품이 있다
- **파트넘버**를 넣는 이유: 붙여 넣는 사람이 있다. `100-100000022BOX`는 0건이었다
- **생성 컬럼인 이유**: 매번 계산하면 GPU 카테고리에서 192ms다. 컬럼으로 두고
  trigram GIN을 걸면 3.5ms다

카탈로그 쪽에도 구분자가 있다는 것이 이번에 드러났다 — `GeForce RTX™ 4070`의
™ 때문에 10건이 `rtx 4070` 검색에서 빠져 있었다. ASCII 밖 문자가 든 이름이 155건이다.

> **두 개의 `squash`가 같아야 한다.** 하나는 TS에, 하나는 생성 컬럼에 있다.
> 어긋나면 **던지지도 않고 그냥 결과가 안 나온다.** 통합 테스트가 두 정의를
> 같은 입력에 걸어 고정한다 (`apps/ingest/test/search-sql.test.ts`).

### 3. ★ 조각으로 쪼개 전부 만족(AND)을 요구한다

"지포스 5080"은 `MSI GeForce RTX 5080 16G …` 안에 통째로 들어있지 않다.
공백으로 쪼개고, 조각마다 이름 어딘가에 있어야 한다.

조각 **안**은 OR이다. 타이핑 중인 「라」는 라이젠일 수도 라데온일 수도 있다.
한쪽으로 단정하지 않는다.

### 4. 타이핑 중인 한글을 앞부분으로 본다

「라이젠」을 치는 동안 화면에는 `라` → `라이` → `라이ㅈ` → `라이제` → `라이젠`이
차례로 나타난다. 앞의 것들이 전부 빗나가면 목록이 글자마다 깜빡인다.

- **앞부분 일치**를 허용한다: `라이` ⊂ `라이젠`
- **마지막 음절의 받침만** 무시한다: `라이제`의 `제`는 `젠`에서 받침을 뗀 것이다
- 조합 중 자모 하나(`ㅈ`)는 앞부분까지만 맞으면 통과시킨다

받침 무시를 **마지막 음절로 한정**하는 것이 중요하다. 가운데까지 풀면
`라이젠스` 같은 것이 엉뚱하게 붙는다.

### 5. ★ 모르는 말을 조용히 버리지 않는다

뜻을 모르는 한글 조각이 있으면 **결과를 0건으로 만든다.**

버리면 "다나와 5080"이 5080 전부를 부른다. 사용자는 자기가 친 말이 무시됐다는
것을 모른 채 목록을 본다. ADR-0016이 세운 선과 같은 방향이다 — **모르는 것을
아는 척하지 않는다.**

화면은 무엇을 모르는지 말한다: "다나와: 카탈로그에서 쓰지 않는 말입니다."

기호만 친 조각(`---`)은 다르다. 눌러두면 빈 문자열이라 `like '%%'`가 되어
**전부 통과**한다. 그건 조건을 만들지 않는 쪽이 맞다 — 검색어가 없는 것과 같다.

### 6. 무엇으로 바꿔 찾았는지 말한다

"라이젠 → ryzen(으)로 찾았습니다." 말하지 않으면 영문 결과가 나오는 것이
우연처럼 보인다. 고르기와 카테고리 목록이 **같은 문장**을 쓴다.

### 7. 고르기와 목록이 같은 해석을 쓴다

`packages/db/src/queries/search.ts`의 `nameWhere` 하나를 양쪽이 쓴다.
두 벌이 되면 "고를 땐 나오는데 목록엔 없다"가 된다. ADR-0010이 규칙 엔진에
대해 말한 것과 같은 이유다.

## 이유

### 왜 형태소 분석기나 전문 검색(FTS)을 쓰지 않는가

| 대안 | 탈락 이유 |
|---|---|
| PostgreSQL FTS (`tsvector`) | 부품 이름은 문장이 아니다. `RTX4070S-O12G`를 어절로 나눌 수 없고, 한국어 사전(`textsearch_ko`)은 설치가 필요한데 관리형 PG에서 보장되지 않는다 |
| 한국어 형태소 분석기 (mecab-ko 등) | Python 워커가 필요하고(Phase 2), 분석해봐야 「지포스」는 미등록어다. 사전을 손으로 넣어야 하는 건 같다 |
| 한글 ↔ 로마자 자동 변환 | 「지포스」 → `jipos`. 카탈로그의 `geforce`와 만나지 않는다. **외래어 표기는 규칙이 아니라 관습이다** |
| 번역 API | 외부 의존이 생기고, 「엠에스아이」를 MSI로 바꿔주지 않는다 |
| `part_aliases`에 한글 행을 넣는다 | 부품 22,962건 × 표기 수만큼 행이 는다. 「지포스」는 부품이 아니라 말이고, 2,784건 전부에 같은 행을 넣을 이유가 없다 |

**이건 사전 문제이지 언어 처리 문제가 아니다.** 손으로 고른 60여 개의 말이
카탈로그의 대부분을 덮는다 (조사 §5).

### 왜 `search_text`를 생성 컬럼으로 두는가

적재에서 채우면 **적재를 거치지 않고 바뀐 행**에서 낡는다. 어드민이 이름을
고칠 수 있고(§5.3), 그때 검색이 조용히 어긋난다. 생성 컬럼은 그럴 수 없다.

스키마 변경은 컬럼 추가뿐이라 **T0**다 (`autonomous-pipeline-plan.md` §7.1).

## 결과

- **사전에 말을 더할 때는 세어보고 넣는다.** 0건이어도 넣을 수 있지만
  그때는 왜인지 적는다 (조사 §5.2)
- **영문 쪽은 이미 눌러둔 모양으로 적는다.** `cooler master`라고 적으면
  절대 안 걸린다. 테스트가 `squash(en) === en`을 고정한다
- **`squash`를 고치면 마이그레이션도 같이 고친다.** 두 정의가 어긋나면
  검색이 조용히 빗나간다. 통합 테스트가 유일한 강제 지점이다
- 사전은 한 표기가 한 영문만 가리킨다. 테스트가 중복을 잡는다
- 카탈로그가 커지면 속도를 다시 잰다 (조사 §6). 지금은 22,962건이다
- **검색어 해석을 새로 만들면 `nameWhere` 한 곳만 고친다.** 고르기와 목록이
  같은 함수를 쓴다
