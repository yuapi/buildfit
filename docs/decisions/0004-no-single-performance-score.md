# ADR-0004: 성능 지표를 단일 점수로 만들지 않는다

## 상태
채택

## 배경

견적 비교 기능(§6.3)을 만들면 "이 견적은 87점" 같은 단일 점수를 내고 싶어진다.
만들기 쉽고, 공유도 잘 되고, 사용자도 그걸 원하는 것처럼 보인다.

문제는 그게 **틀린 답을 자신 있게 내놓는 구조**라는 점이다.
(`pc-builder-spec.md` §6.1)

- 게임은 GPU가 지배한다
- 인코딩·컴파일은 CPU가 지배한다
- 같은 게임이라도 해상도가 올라갈수록 GPU 의존도가 커진다

용도를 빼고 합산하면 의미가 없다. 그리고 사용자는 수십만 원을 쓰는 결정을 한다.

## 결정

**단일 점수를 만들지 않는다.** 대신 다음 원칙을 따른다.

1. **항상 용도 × 해상도 축으로 쪼개서 제시한다**

```
1080p 게임   |  1440p 게임  |  4K 게임
영상 편집     |  컴파일·빌드  |  일반 사무
```

2. **단정적 표현을 쓰지 않는다.** "병목입니다"가 아니라
   "이 해상도에서는 CPU가 먼저 한계에 닿을 가능성이 높습니다" (§6.2)

3. **차이의 크기를 체감 언어로 표현한다.** 숫자만 주면 3% 차이를 큰 것으로 오해한다 (§6.3)

| 성능차 | 표현 |
|---|---|
| ~5% | 체감하기 어려움 |
| 5~15% | 상황에 따라 느낄 수 있음 |
| 15~30% | 뚜렷한 차이 |
| 30%~ | 체급이 다름 |

4. **불확실성을 반드시 표시한다.** 단일 수치가 아니라 예측 구간으로 낸다 (§6.6.4)

| 상황 | 표시 |
|---|---|
| 실측 데이터 존재 | "측정값" + 출처 링크 |
| 유사 조합 다수 존재 | "추정 92~104 fps" (좁은 구간) |
| 데이터 희소 영역 | "추정 80~120 fps · 참고용" (넓은 구간) |
| 추정 불가 | 수치를 내지 않고 상대 비교만 |

5. **"AI 분석" 라벨을 전면에 내세우지 않는다.** 최근 그 표현은 신뢰의 근거가 아니라
   대충 만들었다는 신호로 읽히며, 기대치만 올려놓고 실망을 부른다 (§6.6.6)

## 이유

- **합산은 정보를 파괴한다.** 용도별로 순위가 뒤집히는 두 견적을 한 숫자로 줄이면,
  그 숫자가 어느 용도 기준인지 알 수 없고 사용자는 자기 용도와 무관한 답을 받는다
- **틀려도 납득시키는 것은 AI라는 라벨이 아니라 근거의 투명성이다.** "AI라서 틀렸다"는
  변명이 통하지 않는 금액대다 (§6.6.6)
- **예측 구간의 폭이 곧 신뢰도 표시다.** 데이터 밀도가 낮은 영역에서 넓은 구간이
  나오는 건 결함이 아니라 정직함이다 (§6.6.4)
- **구조적 모델을 쓰면 설명이 따라온다.** §6.6.1의 soft-min 구조
  (`예측 FPS ≈ soft-min(CPU 한계, GPU 한계)`)는 "CPU 한계 145fps, GPU 한계 98fps →
  이 해상도에서는 GPU 제한"처럼 결과를 설명할 수 있다. 단일 점수로 뭉개면 이 설명력이
  사라진다. §6.2 병목 분석이 별도 기능이 아니라 이 모델의 부산물이 되는 것도 같은 이유다

**검토한 대안**

| 대안 | 탈락 이유 |
|---|---|
| 단일 종합 점수 | 용도별로 순위가 뒤집히는 경우를 표현할 수 없다. 공유는 잘 되지만 틀린다 |
| 용도별 점수 + 종합 점수 병기 | 사용자는 결국 종합 점수만 본다. 병기는 완화책이 아니다 |
| 점수 없이 부품 스펙만 나열 | 판단을 돕는다는 목적에 미달. 비교는 해줘야 한다 |
| 블랙박스 회귀로 점수 산출 | 데이터가 수백~수천 건이라 일반화되지 않고, 무엇보다 설명할 수 없다 (§6.6.1) |

## 결과

**제약**

- 결과 화면이 복잡해진다. 용도 × 해상도 축을 UI에서 감당해야 하고, 기본 축을 무엇으로
  둘지 결정이 필요하다
- **공유 유인이 줄어든다.** "87점" 스크린샷만큼 퍼지지 않는다. §6.7 공유 구조와
  검색 유입 설계로 보완한다
- 예측 구간을 내려면 모델이 불확실성을 산출해야 한다. GBM 계열 또는 제약을 건
  파라메트릭 모델을 쓰고, 딥러닝은 데이터 규모상 부적합하다 (§6.6.3)
- 벤치마크 수치는 **출처를 명시하고 원문을 링크한다.** 측정값과 추정값을 라벨로 구분한다
- **시드 데이터가 없으면 Phase 3 자체가 성립하지 않는다.** 시드 확보가 불가능하면
  이 Phase를 미룬다. 근거 없는 점수를 지어내지 않는다 (§6.8)

**후속 작업 (Phase 3, 단 일부는 그 전에)**

- 용도 축 최종 목록 확정, 기본 선택값 결정
- 벤치마크 시드 데이터 확보 경로 + 인용 가능 범위 라이선스 확인
- **FPS 제보 수집을 Phase 3 이전에 시작한다.** 데이터가 쌓이는 데 시간이 걸린다 (§6.6.5)
- 성능 예측 모델 검증 기준: 홀드아웃 세트 대비 오차. 기준 초과 시 이전 모델 버전
  유지하고 배포 차단 (`pipeline-plan.md` 연계, §10.4)
