# ADR-0005: localStorage 저장 포맷은 add-only

## 상태
채택

## 배경

회원가입이 없으므로(ADR-0001) 지속성은 브라우저 localStorage가 담당한다. 여기서
서버에는 없는 문제가 생긴다.

**서버는 롤백되지만 사용자 브라우저의 데이터는 롤백되지 않는다.**
(`pc-builder-spec.md` §8A.2, §10.5)

배포를 되돌리면 서버 코드만 구버전으로 복귀하고, 사용자 브라우저에는 신버전 포맷으로
쓰인 데이터가 그대로 남는다. 즉 **구버전 코드가 신버전 데이터를 읽는 상황**이 롤백할
때마다 발생한다. `pipeline-plan.md` §7이 다루는 가역성은 서버 측 이야기이며 클라이언트에는
적용되지 않는다.

이 비대칭은 자가수복 파이프라인과 정면으로 충돌한다. 자가수복 루프가 저장 포맷을
바꿔놓고 롤백하면, 롤백으로 복구되지 않는 피해가 사용자 브라우저에 남는다.

## 결정

**저장 포맷을 add-only로 고정한다.** 서버 스키마의 expand-contract와 같은 원칙이다.
(`pc-builder-spec.md` §8A.2)

1. **필드를 추가할 수는 있어도 의미를 바꾸거나 제거하지 않는다**
2. **읽기는 관대하게.** 모르는 필드는 무시하고, 없는 필드는 기본값으로 채운다.
   구버전 코드가 신버전 데이터를 만나도 깨지지 않아야 한다
3. **모든 레코드에 `v` 필드.** 읽을 때 버전을 보고 필요하면 마이그레이션
4. **파싱 실패는 조용히 폐기.** 견적 하나가 깨졌다고 앱 전체가 죽으면 안 된다.
   try/catch로 감싸고 실패한 항목만 버린다
5. **포맷 변경은 T2(승인 필수)로 분류한다.** 되돌릴 수 없는 변경이다

```javascript
// 읽기 패턴
function loadBuilds() {
  try {
    const raw = localStorage.getItem('builds');
    if (!raw) return [];
    const parsed = JSON.parse(raw);
    return parsed
      .map(migrate)          // 버전별 마이그레이션
      .filter(Boolean);      // 복구 불가 항목 제거
  } catch {
    return [];               // 앱은 계속 동작
  }
}
```

추가로 **자가수복 루프가 저장 포맷을 임의로 바꾸지 못하게** 한다. `pipeline-plan.md`
§6.5 즉시조치 화이트리스트에서 제외한다. (§10.5)

## 이유

- **롤백 비대칭이 유일하게 비가역인 지점이다.** 이 프로젝트는 금전 거래도 개인정보도
  없어서(§10.6) 대부분의 사고가 되돌릴 수 있는데, 클라이언트 저장 데이터만 예외다.
  비가역 작업은 승인으로 해결할 문제가 아니라 **설계로 우회할 문제**다
  (`pipeline-plan.md` §7)
- **add-only면 어느 방향으로 읽어도 깨지지 않는다.** 구버전 코드는 모르는 필드를
  무시하면 되고, 신버전 코드는 없는 필드를 기본값으로 채우면 된다. 양방향 호환이
  규칙 하나로 확보된다
- **서버 스키마와 같은 원칙이라 판단이 단순해진다.** expand만 자동, contract는 T2.
  클라이언트와 서버에 다른 기준을 두면 어느 쪽 규칙인지 매번 헷갈린다
- **조용한 폐기가 맞는 이유**: 저장된 견적은 편의 기능이고 정본은 공유 URL이다(§8A.3).
  항목 하나를 잃는 비용보다 앱이 안 뜨는 비용이 훨씬 크다

**검토한 대안**

| 대안 | 탈락 이유 |
|---|---|
| 자유롭게 바꾸고 마이그레이션으로 해결 | 마이그레이션은 앞으로만 간다. 롤백 시 구버전 코드에는 그 마이그레이션 코드가 없다 |
| 버전 불일치 시 저장 데이터 초기화 | 롤백 한 번에 전 사용자의 저장 견적이 날아간다 |
| 서버에 저장 | ADR-0001 위반. 개인정보·계정이 생긴다 |
| 키를 잘게 나눠 필드별로 관리 | 일관성 깨진 상태가 생긴다. 목록 전체를 한 키에 담는다 (§8A.4) |

## 결과

**제약**

- 잘못 설계한 필드를 제거할 수 없다. **초기 스키마 설계에 신중해야 한다**
- 저장 상한을 두고 초과 시 오래된 것부터 제거한다 (LRU). 상한은 §8A.1 기준
  (`builds` 20개, `recent_builds` 5개, `recent_parts` 20개)
- 마이그레이션 함수가 버전마다 누적된다. 제거할 수 없으므로 코드가 길어지는 것을 감수한다
- 포맷 변경이 T2이므로 **자가수복 루프가 단독으로 처리할 수 없다.** 승인 대기 동안
  관련 수복이 막힐 수 있다
- 시크릿 모드·스토리지 차단·용량 초과 시 쓰기가 실패한다. **저장 실패를 정상 경로로
  처리**하고 "이 브라우저에서는 저장할 수 없습니다" 정도로 안내한다 (§8A.4)

**후속 작업**

- localStorage 스키마 v1 정의 (`builds` / `recent_builds` / `recent_parts` / `prefs` /
  `schema_version`)
- `migrate(record)` 함수 골격과 버전 라우팅
- **회귀 테스트에 구버전 데이터를 심어둔 상태에서의 동작을 반드시 포함한다.
  이것이 유일한 방어 수단이다** (§10.5)
- **과거 모든 버전의 샘플 데이터를 보관하고, 배포마다 전 버전이 정상 복원되는지
  검증한다** (§10.4)
- 카오스 카탈로그에 "잘못된 포맷의 localStorage 데이터" 항목 추가
  (`pipeline-plan.md` §12.2 #11과 연결)
- 합성 트래픽 시나리오 7번: 구버전 포맷 데이터를 심어둔 상태로 진입 → 마이그레이션
  동작 확인 (§10.1)
