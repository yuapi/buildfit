## 1. 한 줄 정의

**"이 조합, 문제 없나?"에 답하는 도구.** 가격 비교가 아니라 판단을 돕는다.

### 1.1 안 하는 것

- 가격 비교 커머스 (다나와·에누리 영역, 개인이 경쟁 불가)
- 쇼핑몰 제휴 기반 최저가 나열
- 부품 판매 또는 중개

### 1.2 하는 것

조합을 입력받아 **살 수 있는 조합인지, 낭비가 없는지, 유지비가 얼마인지**를 알려준다.

### 1.3 타겟

- 처음 조립하는 사람 — 뭐가 안 맞는지 모름
- 업그레이드하는 사람 — 기존 부품과의 호환이 관건
- 견적 게시판에 물어보기 전에 스스로 검증하고 싶은 사람

## 2. 차별점 세 가지

경쟁 도구(다나와 견적, PCPartPicker)가 약한 지점에만 집중한다.

### 2.1 한국 누진세 기반 전기요금 ★ 최우선

이게 가장 명확한 차별점이다. 해외 도구는 kWh당 단가를 곱할 뿐이고, 다나와 견적은 아예 다루지 않는다.

핵심은 **PC 전력만 따로 계산하면 의미가 없다**는 점이다. 한국 주택용 전력은 누진 구간이 있어서, 가구 전체 사용량에 PC 사용분이 얹히면서 구간이 넘어가는지가 실제 체감 요금을 결정한다.

```
입력: 평소 월 전기 사용량(kWh) + PC 사용 패턴(게임 n시간/일, 아이들 m시간)
계산: PC 추가 사용량 → 기존 사용량에 합산 → 누진 구간 재계산
출력: 월 추가 요금, 누진 구간 상승 여부, 구간 상승 시 경고
```

> **확보 완료 (2026-09-22).** 사용자가 한전 사이버지점 화면을 직접 열어 캡처해
> 주었다 — 이 실행 환경의 네트워크 정책이 한전 도메인을 차단해 그때까지 구할 수
> 없던 표다. 요율표·계절별 구간 차이·슈퍼유저요금까지 `docs/research/kepco-tariff.md`에
> 있고, 계산은 `packages/compat/src/electricity.ts`다.
>
> **고압은 담지 않는다.** 받은 화면의 고압 표는 적용일자가 2021년이고, 아파트
> 단일·종합계약은 세대 요금을 관리주체가 산정해 관리비로 청구한다 — 사용자가
> 직접 확인할 수 있는 값이 아니다.
>
> 기후환경요금·연료비조정요금·부가세·전력산업기반기금은 **담지 않는다.** 앞의 둘은
> 분기마다 바뀌고 뒤의 둘은 그 화면에 없다. 그래서 이 계산은 실제 청구액보다
> 낮고, **그 방향을 결과에 적는다.**

부가 기능으로 "전기요금까지 포함한 3년 총소유비용" 비교가 가능하다. 저효율 부품이 초기 가격 차이를 유지비로 역전하는 경우를 보여줄 수 있다.

### 2.2 호환성 규칙의 깊이

단순 소켓 체크를 넘어 실제로 조립하다 막히는 지점을 다룬다. 상세 카탈로그는 §4.

### 2.3 견적 단위 성능 비교

부품 대 부품 비교 도구는 이미 여럿 있지만(HWbattle 등), **완성된 견적끼리 비교하는 곳은 없다.** 사용자의 실제 의사결정 단위는 부품이 아니라 조합 전체다.

여기에 "차액을 어디에 쓰는 게 나은가"까지 답하면 단순 비교를 넘어선다. §6 참조.

## 4. 호환성 규칙 카탈로그

구현 우선순위 순. 규칙 하나가 곧 테스트 케이스 하나가 된다.

> **구현 시 참조: `docs/compat-rules.md`**
> Phase 0 규칙 8개의 정확한 입력 필드·판정식·판정 불가 조건·데이터 함정을 확정해
> 둔 문서다. 이 절은 무엇을 판정하는지를 정하고, 어떻게 판정하는지는 그쪽에 있다.

### 4.1 필수 (Phase 0)

| # | 규칙 | 필요 데이터 |
|---|---|---|
| 1 | CPU 소켓 = 메인보드 소켓 | 소켓명 |
| 2 | 메모리 규격 (DDR4/DDR5) 일치 | 규격, 슬롯 수 |
| 3 | 메모리 모듈 수 ≤ 슬롯 수 | 슬롯 수 |
| 4 | GPU 길이 ≤ 케이스 GPU 최대 길이 | mm |
| 5 | 메인보드 폼팩터 ⊂ 케이스 지원 목록 | ATX/mATX/ITX |
| 6 | PSU 폼팩터 ⊂ 케이스 지원 | ATX/SFX |
| 7 | 소비전력 대비 PSU 정격 (구간 판정) | CPU TDP/PPT, GPU TDP + 보드·메모리는 **범위 가정** |
| 8 | PCIe 보조전원 커넥터 수 충족 | 8핀/12VHPWR 개수 |

#### 규칙 7은 점 값이 아니라 구간으로 판정한다 ★

메인보드 소비전력은 1차 소스에 필드가 없고, 공개 자료도 **25~80W로 3배 차이**가 난다
(`docs/research/power-constants.md`). 여기서 점 값을 하나 고르면 그 숫자에는 근거가
없고, 규칙 7은 오류 등급이라 틀리면 사용자가 멀쩡한 파워를 못 쓴다고 판단하거나
부족한 파워를 괜찮다고 믿는다.

ADR-0004와 §6.6.4가 성능 예측에 대해 정한 원칙 — **단일 수치를 내놓지 않는다,
구간의 폭이 곧 신뢰도 표시다** — 을 전력에도 적용한다.

```
총_최소 = CPU + GPU + 보드_최소 + 메모리_최소 × 모듈수
총_최대 = CPU + GPU + 보드_최대 + 메모리_최대 × 모듈수

PSU 정격 ≥ 총_최대 × 1.3   →  통과   여유 있음
총_최소 ≤ PSU < 그 값       →  경고   가정에 따라 갈림. 넉넉한 쪽을 권함
PSU < 총_최소               →  오류   가정을 아무리 낮게 잡아도 부족
```

- CPU는 `PPT`(실측 최대)가 있으면 그쪽을 쓴다. TDP는 실사용 피크를 과소평가한다
- **결과 화면에 가정 범위와 출처를 함께 노출한다.** 사용자가 왜 그 판정이 나왔는지
  확인할 수 있어야 한다
- 경계 구간이 넓게 나오는 것은 결함이 아니라 데이터가 그만큼 없다는 표시다.
  가정 범위가 좁혀지면 경고 구간도 자연히 줄어든다
- 스토리지·팬 상수는 MVP 취급 부품(6종)에 없으므로 Phase 1에서 해당 부품이
  추가될 때 확정한다

### 4.2 경고 수준 (Phase 1)

| # | 규칙 | 비고 |
|---|---|---|
| 9 | CPU 쿨러 높이 ≤ 케이스 최대 높이 | 공랭 |
| 10 | 라디에이터 크기 ⊂ 케이스 장착 위치 | 수랭, 두께도 포함. **Phase 2 이후** — 아래 참조 |
| 11 | 메모리 높이 vs 쿨러 간섭 | 히트싱크 큰 램 |
| 12 | BIOS 업데이트 필요 여부 | 보드·CPU 출시연도 + BIOS Flashback 유무 |
| 13 | M.2 슬롯 사용 시 SATA 포트 비활성화 | 칩셋별 상이 |
| 14 | PCIe 레인 분배 (GPU x8로 떨어지는 경우) | |
| 15 | GPU 두께(슬롯) ≤ 케이스 확장 슬롯 수 | 오류 등급. **97.0% 판정 가능** — 아래 참조 |
| 16 | 총 메모리 용량 ≤ 보드·CPU 최대 | **99.7% 판정 가능** — 아래 참조 |
| 17 | M.2 드라이브를 보드가 받는가 | 오류. 19.9% — **개수는 못 센다** |
| 18 | SATA 드라이브 수 ≤ 보드 SATA 포트 수 | 오류. 75.1% |
| 19 | 3.5"·2.5" 드라이브 수 ≤ 케이스 베이 수 | 3.5"는 오류, 2.5"는 경고. 99.4% |
| 20 | 쿨러가 CPU 소켓을 지원하는가 | 경고. **99.9% 판정 가능** — 아래 참조 |

12번이 실제로 가장 많이 겪는 함정이다. 보드는 맞는데 BIOS가 구버전이라 부팅이 안 되는 상황.

**15번은 규칙 목록에 빠져 있던 것을 메운다.** 두꺼운 GPU가 작은 케이스에 안 들어가는
것은 실제로 자주 겪는 실패인데 규칙 4는 **길이**만 본다. 두께를 아무도 안 봤다.

필요한 두 필드가 양쪽 다 99% 가까이 채워져 있어, **케이스가 얽힌 규칙 중 지금 바로
거의 다 판정되는 유일한 규칙이다** (판정 불가 3.04%. 규칙 6은 83%, 규칙 9는 75%).
케이스 데이터 보강(§5.3)을 기다리지 않아도 된다.

```
필요 슬롯 = ceil(GPU total_slot_width)
필요 슬롯 > 케이스 expansion_slots  →  오류
```

두 가지를 주의한다.

- **`case_expansion_slot_width` 필드를 쓰지 않는다.** 이름은 딱 맞지만 값이 틀렸다.
  두 필드가 다 있는 1,518건 중 **48.8%에서 「차지하는 슬롯 수」가 「카드 두께」보다
  작다.** 물리적으로 불가능한 값이다. `total_slot_width`에서 유도한다
- **필요조건이지 충분조건이 아니다.** `expansion_slots`는 뒷면 구멍의 총 개수이고,
  GPU가 꽂히는 위치는 보드의 x16 슬롯 위치에 달려 있다. 넘으면 확실히 안 들어가지만,
  통과했다고 반드시 들어가는 것은 아니다. 문구에 이 한계를 적는다

근거: `docs/research/gpu-slot-width.md`

**16번도 빠져 있던 것을 메운다.** `memory_max_gb`가 CPU·보드 양쪽에 적재돼 있고
부품 화면에 「최대 메모리」로 표시까지 되는데 **어떤 규칙도 쓰지 않았다.** 규칙 2는
DDR 규격을, 규칙 3은 모듈 수를 본다. 용량은 아무도 안 봤다.

```
한계 = min(보드 최대, CPU 최대)
총 용량(킷 합계) > 한계  →  경고
```

- **CPU도 본다.** 소켓이 맞는 조합의 **14.2%에서 CPU의 최대가 보드보다 낮다.**
  보드만 보면 그만큼을 놓친다
- **오류가 아니라 경고다.** 제조사 사양은 보수적이고 BIOS 업데이트로 늘어난다.
  규칙 9와 같은 이유다 (§9.1)
- **작은 값을 이상치로 거르지 않는다.** 최대 4GB는 LGA775·Atom 보드에서 맞는 값이고
  22건이 실재한다. 대신 **슬롯 수와 맞대 본다** — 최대 용량이 슬롯 수보다 작을 수는
  없다. 이 검사가 틀린 5건만 정확히 걸러 낸다

규칙 2·3을 통과하는 조합 6,316,250건 중 **75,497건(1.20%)이 용량을 넘긴다.**
지금은 전부 "문제 없음"으로 나온다.

근거: `docs/research/memory-capacity-limit.md`

**17·18·19는 스토리지 슬롯을 연다.** 스토리지는 "규칙 7(전력)과 규칙 13(칩셋)이 둘 다
막혀 있어 판정에 기여하지 않는다"는 이유로 보류돼 있었다. **그 둘 말고 셋이 더 있고
데이터가 전부 채워져 있다.**

| 규칙 | 보는 것 | 판정 가능 |
|---|---|---|
| 17 | M.2 드라이브를 보드가 받는가 | 19.9% |
| 18 | SATA 드라이브 수 ≤ 보드 SATA 포트 수 | 75.1% |
| 19 | 3.5"·2.5" 드라이브 수 ≤ 케이스 베이 수 | 99.4% |

**17은 개수를 세지 않는다.** `m2_slots` 배열 길이가 슬롯 수가 아니다 — 한 슬롯을
크기마다 행으로 쪼갠 레코드와 덜 적은 레코드가 섞여 있어 138개 계열이 서로 다른
행 수로 존재한다. 믿을 수 있는 것은 **있다 / 없다**뿐이다 (`docs/compat-rules.md` §17.4).

**전력은 그대로 막혀 있다.** NVMe·SATA의 전력 범위는 출처를 확보하지 못했으므로
규칙 7은 스토리지를 계산에 넣지 않고, **넣지 않았다는 사실을 결과에 적는다**
(§7.4가 가정 범위와 출처를 싣는 것과 같은 방식). 추정치를 지어내지 않는다.

같은 `0`이라도 필드마다 뜻이 다르다는 것이 이 셋의 핵심이다. 보드의 M.2 `0`은
값이고(DDR2의 100%, DDR3의 86.3%가 그렇다), SATA `0`은 미입력이다(세대별 경향이
없이 24.9%). **세대별 분포를 봐야 갈린다.**

근거: `docs/research/storage-slots.md`

**20도 빠져 있던 것을 메운다** (이슈 #17). 「이 쿨러가 AM5를 지원하나」는 조립에서 가장
흔히 겪는 실패 중 하나인데 아무 규칙도 보지 않았다. 쿨러 **99.9%**(2,389/2,392)가 지원
소켓 목록을 갖고 있고 적재·표시까지 되고 있었다. 규칙 15·16과 같은 모양이다.

| CPU 소켓 | 「목록에 없음」 (CPU × 쿨러 전수) |
|---|---|
| AM5 | 27.1% |
| LGA 1700 | 28.1% |
| LGA 1851 | 33.1% |

**오류가 아니라 경고다.** AM5가 없는 쿨러 647개 중 363개(56%)가 AM4는 적고 있다.
AM4 쿨러 상당수가 AM5에도 맞는다고 알려져 있지만 **데이터로 증명되지 않는다.** 그래서
그 관계로 묶지도, 오류로 단정하지도 않는다 — 아는 것은 「목록에 없다」뿐이다.

경고 규칙이라 **고르기에서 숨기지 않는다** (ADR-0016).

근거: `docs/compat-rules.md` §20

> **구현됨** (`docs/compat-rules.md` §12). 다만 보드 출시 연도는 아래 추정보다 나쁘다 —
> 전수의 **79.6%가 결측**이라 실제로는 82%가 판정 불가로 뜬다.

**10번은 Phase 1에서 뺀다.** 1차 소스인 OpenDB 케이스 스키마에 라디에이터·팬 장착
필드가 **아예 없다**. 값이 비어 있는 게 아니라 필드가 존재하지 않으므로, 업스트림
기여(§5.7)로 메우려 해도 스키마 변경이 선행되어야 한다. 경고 등급이고 수랭 비중이
제한적이므로 Phase 2 이후로 미루고, 그 전까지는 국내 인기 케이스 20~30종에만 수동
입력해 선별 적용한다. 쿨러 쪽 `radiator_size`는 존재하므로 막히는 것은 케이스 한 면뿐이다.
근거: `docs/research/opendb-schema-analysis.md` §7.2

**12번의 우회책에 신호를 하나 더 쓴다.** 출시연도 비교만으로는 같은 해 출시 조합을
가릴 수 없고, OpenDB의 보드 출시연도는 현행 세대에서도 40% 결측이다. 대신 BIOS
Flashback 유무가 99% 채워져 있어 **경고의 심각도를 나눌 수 있다**.

```
CPU 출시연도 > 보드 출시연도  AND  Flashback 없음  → 경고 (CPU 없이 업데이트 불가)
CPU 출시연도 > 보드 출시연도  AND  Flashback 있음  → 정보 (업데이트가 필요할 수 있음)
보드 출시연도 결측                                → 판정 불가 (§4.3)
```

### 4.3 판정 등급

- **오류**: 물리적으로 불가능. 조립 자체가 안 됨
- **경고**: 가능하지만 확인 필요. 간섭 가능성, 성능 손실
- **정보**: 알아두면 좋은 사항
- **판정 불가**: 판정에 필요한 데이터가 없음. ★ 아래 참조

#### 판정 불가 ★

**데이터가 없을 때 규칙을 조용히 통과시키지 않는다.** 결측을 통과로 처리하면 사용자는
"호환 확인됨"을 보고 안 맞는 부품을 산다. 이것이 이 도구가 낼 수 있는 가장 나쁜
결과다 (§5.3: 스펙 오류는 사용자가 실제로 부품을 잘못 사게 만든다).

`autonomous-pipeline-plan.md` §9.6이 관측 표본 부족을 "이상 없음"이 아니라 "판정 불가"로
처리하라고 한 것과 같은 원칙이다.

- 필요 필드가 하나라도 비어 있으면 그 규칙은 **판정 불가**로 표시한다
- 어느 부품의 어느 항목이 없어서 판정하지 못했는지 **명시**한다
- 결과 요약에서 "모든 검사 통과"라고 쓰지 않는다. 통과 n건 / 판정 불가 m건으로 나눈다
- 판정 불가 항목은 §5.5의 오류 신고·빈 필드 보강 대상 큐로 연결한다

실제로 이 등급이 필요하다는 것은 조사에서 확인됐다. 규칙 6(PSU 폼팩터)에 필요한
케이스 필드가 현행 세대에서도 83% 결측이다.
근거: `docs/research/opendb-schema-analysis.md` §7.5

## 5. 데이터 — 이 프로젝트의 진짜 관문

로직은 며칠이면 짜지만 데이터는 계속 일이다. **여기서 포기하지 않는 것이 성패를 가른다.**

### 5.1 카테고리별 필요 필드와 난이도

| 카테고리 | 난이도 | 핵심 난점 |
|---|---|---|
| PSU | 하 | 커넥터 구성만 정확하면 됨 |
| CPU | 하 | 공식 스펙이 명확하고 종수가 적음 |
| 메모리 | 중 | **히트싱크 높이 데이터가 거의 없음** |
| 쿨러 | 중 | 소켓 호환 목록이 길고 개정판이 많음 |
| 케이스 | 중상 | 표기 치수와 실제 여유가 다름 |
| GPU | 상 | **AIB 모델마다 물리 치수가 전부 다름** |
| 메인보드 | 최상 | **BIOS 버전별 CPU 지원표가 비정형** |

#### CPU
```
소켓, 세대, 코어/스레드, 기본·부스트 클럭, TDP, PPT(실측 최대),
내장그래픽 유무, 지원 메모리 규격·속도, PCIe 버전, 번들 쿨러 유무
```
출처는 제조사 공식 스펙. 현행 세대 기준 25종 내외라 하루면 끝난다.

#### GPU — 물리 치수는 해소, 성능 필드는 부분 해소
```
[칩 레벨]  칩셋명, VRAM, 기준 TDP, 권장 PSU, 기준 성능 점수
[AIB 레벨] 길이, 두께(슬롯 수), 높이, 보조전원 커넥터 구성, 실제 TDP
```

**같은 4070이라도 제조사·모델마다 길이가 240mm에서 340mm까지 벌어진다.** 케이스 호환
판정이 이 값에 달려 있어, 원래는 AIB 모델을 전부 수집하는 건 개인이 감당할 규모가
아니라고 보고 칩 레벨 + 인기 AIB 3~5개로 우회할 계획이었다.

**그 전제가 틀렸다.** OpenDB 조사 결과 현행 세대(RTX 40/50, RX 7600 이상) **AIB
1,344개 모델 전량이 `length`를 갖고 있고**(100%), 두께(`total_slot_width`) 99.9%,
TDP 100%, 보조전원 커넥터 구성도 97% 이상이다. 수집 부담이 사실상 0이다.
근거: `docs/research/opendb-schema-analysis.md` §4, §7.1

**대응 전략 (수정됨)**
- **AIB 모델을 전량 적재한다.** 인기 모델만 고르지 않는다
- 칩 레벨은 별도 레코드를 만들지 않고 `chipset` 값으로 그룹핑해 유도한다
  (OpenDB는 AIB 단일 계층이고 칩은 문자열 필드다 — §5.8 참조)
- "길이 직접 입력"은 유지하되 **예외 경로로 격하.** OpenDB에 없는 구형·특수 모델용
- 범위 경고("모델에 따라 220~350mm")는 **사용자가 칩만 고른 경우에만** 적용한다.
  AIB를 고르면 확정값으로 판정한다

이 변경은 §2.2(호환성 규칙의 깊이)를 **더 강하게** 만든다. 경쟁 도구가 약한 물리 간섭
검증을 범위 추정이 아니라 확정값으로 할 수 있다.

**단 해소된 것은 물리 치수까지다.** 같은 칩이라도 AIB 모델마다 성능이 다르고
(RTX 4090 부스트 클럭이 2235~2670MHz로 약 19% 차이), §6.6.1이 요구하는
`g(연산 유닛, 클럭, 메모리 대역폭, VRAM, 해상도)` 중 **연산 유닛(56%)과 메모리
대역폭(버스 폭 33%)이 부족하다.** 둘 다 칩 레벨 값이라 칩 276종만 보강하면 되지만,
보강 전에는 Phase 3가 성립하지 않는다.
근거: `docs/research/opendb-schema-analysis.md` §9.2

#### 메인보드 ★ BIOS 문제
```
소켓, 칩셋, 폼팩터, 메모리 슬롯 수·규격·최대 속도·최대 용량,
M.2 슬롯 수와 레인 공유 관계, SATA 포트 수, PCIe 슬롯 구성,
VRM 단수(참고), CPU 지원 최소 BIOS 버전
```

마지막 항목이 최악이다. 제조사마다 "CPU Support List" 페이지 형식이 제각각이고, 표·PDF·아코디언이 섞여 있다. 구조화된 형태로 제공하는 곳이 없다.

**대응 전략**
- Phase 0에서는 **세대 기반 경고만.** "이 CPU는 보드보다 나중에 나왔습니다. BIOS 업데이트가 필요할 수 있습니다" 수준
- 정확한 BIOS 버전 매핑은 Phase 2 이후로 미룬다
- 우회책: 보드 출시일과 CPU 출시일을 비교해서 CPU가 더 나중이면 경고
- **여기에 BIOS Flashback 유무를 함께 쓴다.** 출시일 비교만으로는 부족하다는 것이
  조사에서 확인됐다 — OpenDB의 보드 출시 정보는 **연 단위**라 같은 해 조합을 가릴 수
  없고, 현행 세대에서도 40% 결측이다. 반면 `bios_features.flashback`은 99% 채워져
  있고, Flashback이 있으면 CPU 없이 BIOS를 올릴 수 있어 **경고의 심각도가 달라진다**.
  판정식은 §4.2 참조. 출시연도가 없으면 경고가 아니라 **판정 불가**(§4.3)로 처리한다
  근거: `docs/research/opendb-schema-analysis.md` §7.4

M.2와 SATA 레인 공유도 칩셋·보드마다 다르고 매뉴얼 각주에만 있다. 이것도 Phase 2로 미룬다.

#### 케이스
```
지원 폼팩터, GPU 최대 길이, 쿨러 최대 높이, PSU 최대 길이,
라디에이터 지원(위치별 크기), 전면/상단/후면 팬 규격, 3.5"/2.5" 베이
```

제조사 표기가 낙관적인 경우가 많다. GPU 340mm라고 써도 전면 팬이나 케이블 때문에 실제로는 320mm가 한계인 식이다.

**대응: 표기값을 쓰되 경고 임계에 여유를 둔다.** 표기값의 95% 이상이면 "빠듯할 수 있음" 경고. 라디에이터는 두께 제약이 특히 부실하니 별도 주의 문구.

#### PSU / 메모리 / 쿨러
```
PSU    정격, 80+ 등급, 폼팩터, 길이, 모듈러, PCIe 8핀 수, 12VHPWR 유무
메모리  규격, 키트 구성, 총 용량, 속도, 타이밍, 전압, 높이(mm)
쿨러    타입(공/수랭), 높이 또는 라디에이터 크기, 지원 소켓, TDP 대응
```

메모리 높이는 공개 데이터가 부실하다. 히트싱크 없는 모델은 32mm 내외로 두고, 높은 히트싱크 모델만 개별 기입한다.

### 5.2 부품 식별자 문제

같은 부품이 표기마다 다르다.

```
"RTX 4070 SUPER"
"지포스 RTX 4070 슈퍼"
"GeForce RTX 4070 Super 12GB"
"MSI 지포스 RTX 4070 SUPER 게이밍 X 슬림 D6X 12GB"
```

**canonical slug를 부품마다 하나씩 부여**하고, 표기 변형은 전부 `part_aliases`에 모은다. 이 테이블이 §7 가격 정규화의 입력이자 검색 유입용 URL의 근거가 된다.

```
slug 규칙: 소문자, 하이픈, 제조사-모델-변형
  예) amd-ryzen-7-7800x3d
      nvidia-rtx-4070-super
      msi-mag-b650-tomahawk-wifi
```

### 5.3 수집 전략 — 반자동

전량 수동은 지치고, 전량 자동은 정확도가 안 나온다. **중간을 택한다.**

```
1. 1차 적재: BuildCores OpenDB clone → JSON 파싱 → parts 테이블
2. 국내 유통 판정: §5.7.1 매칭 파이프라인 → skus 생성
3. 빈 필드 확인: 물리 치수 등 누락 항목 목록화
4. 2차 보강: 어드민에 제조사 스펙시트 URL 붙여넣기
   — OpenDB에 주소가 있으면 적재가 `parts.manufacturer_url`에 담아 이 단계를
   대신한다. 어드민이 링크와 출처 기본값을 함께 제공한다 (4,201건, §5.3.1)
5. Claude가 페이지를 읽고 빈 필드를 구조화해서 추출
6. 사람이 확인·수정 후 승인
7. source_url + verified_at 기록하며 저장
```

1~2번이 자동이므로 **수동 작업은 3~7번의 빈 필드 보강으로 한정된다.** 어드민은 여전히 필요하지만 처음부터 전부 입력하는 게 아니라 구멍을 메우는 도구가 된다.

**3~4번을 건너뛰지 않는다.** 스펙 오류는 사용자가 실제로 부품을 잘못 사게 만드는 결과로 이어지므로, 자동 추출을 그대로 신뢰하지 않는다.

#### 5.3.1 제조사 스펙 주소

OpenDB `general_product_information.manufacturer_url`을 `parts.manufacturer_url`에
적재한다. 보강에서 가장 오래 걸리는 단계가 출처를 찾는 것인데, 이 값이 있으면
그 단계가 사라진다. 어드민은 이 주소를 **열기 링크**와 **출처 칸의 기본값**으로
동시에 제공한다.

| 카테고리 | 주소 있음 / 전체 |
|---|---|
| CPU | 655 / 789 (83%) |
| GPU | 938 / 3,837 (24%) |
| PCCase | 812 / 3,782 (21%) |
| RAM | 869 / 4,876 (18%) |
| Motherboard | 560 / 3,701 (15%) |
| CPUCooler | 278 / 2,404 (12%) |
| PSU | 89 / 3,297 (3%) |

**기본값을 넣었다고 확인한 것이 되지는 않는다.** 그래서 값을 감추지 않고 편집
가능한 입력에 그대로 둔다. 작업자가 다른 출처를 썼다면 고칠 수 있어야 한다.

`http(s)`가 아닌 스킴은 적재에서 버린다. 화면에서 링크가 되는 값이다.

이 워크플로를 **Phase 0에서 가장 먼저 만든다.** 견적 도구보다 먼저다. 데이터 입력이 편해야 100개를 채울 수 있고, 데이터가 없으면 도구가 동작하지 않는다.

#### 5.3.2 어드민 접근 제어

어드민은 **부품 스펙을 고치는 화면**이다. 스펙 한 값이 바뀌면 판정이 뒤집히고,
사용자는 그 판정을 믿고 부품을 산다. 공개해 두지 않는다.

**공유 비밀 하나를 HTTP Basic으로 받는다. 계정은 만들지 않는다** (ADR-0001, ADR-0020).

| `ADMIN_TOKEN` | 개발 | 배포본 |
|---|---|---|
| 없음 / 16자 미만 | 그냥 열린다 | `/admin`이 통째로 404 |
| 16자 이상 | 비밀을 묻는다 | 비밀을 묻는다 |

- 아이디 칸은 보지 않는다. 계정이 아니라 비밀이다
- 환경변수를 빠뜨린 배포가 편집기를 공개하지 않도록 **꺼진 쪽이 기본값이다**
- 화면(`proxy.ts`)과 서버 동작(`saveSpecAction`) **양쪽에서** 막는다.
  한 곳만 막으면 그 한 곳이 빗나갈 때 스펙이 고쳐진다
- 비밀 하나이므로 **누가 고쳤는지는 남지 않는다.** 대신 모든 저장이 `source_url`과
  `verified_at`을 남기므로 무엇이 왜 그 값인지는 항상 남는다 (§5.5)

배포는 HTTPS여야 한다. Basic은 비밀을 평문으로 보낸다.


### 5.4 초기 범위

전량을 채우려 하면 시작도 못 한다. **현행 인기 부품 100~150개로 출발한다.**

```
CPU      현행 2세대 × AMD/Intel     약 25종
메인보드  주요 칩셋 × 주요 제조사      약 30종
메모리    DDR4/DDR5 주요 키트         약 15종
GPU      칩 15종 + 인기 AIB 20종     약 35종
케이스    인기 모델                   약 20종
파워      인기 모델                   약 20종
```

선정 기준은 **국내 커뮤니티 견적에 실제로 자주 등장하는 것.** 스펙상 좋은 부품이 아니라 사람들이 실제로 사는 부품이다.

다만 OpenDB 적재가 자동이므로 실제로는 **전량을 넣고 §5.7.1 유통 판정으로 거르는 편이 낫다.** 위 숫자는 '수동 보강을 우선할 대상'의 규모로 읽는다.

### 5.5 정확도 유지

- **모든 필드에 `source_url`과 `verified_at`.** 나중에 재검증할 때 출처가 없으면 처음부터 다시 해야 한다
- 각 부품 페이지에 **오류 신고 버튼.** 사용자 제보가 가장 값싼 검증 수단이다
- 신고가 들어오면 해당 필드에 `disputed` 플래그를 세우고, 결과 화면에 "검증 중" 표시
- **신고 말고도 데이터 안에서 나오는 신호가 있다.** 정답을 몰라도 「어딘가 틀렸다」는
  알 수 있는 경우다. 적재가 스스로 세우고, 사라지면 거둔다
  - 같은 제품의 중복 레코드끼리 값이 어긋난다 (이슈 #11)
  - 출시 연도가 그 소켓이 나오기 전이다 (이슈 #18, `docs/research/release-year-plausibility.md`)
  - 메모리의 모듈 수 × 모듈 용량 ≠ 총 용량이거나 이름의 구성과 다르다 (이슈 #20)
- **「검증 중」은 판정을 바꾸지 않는다** (ADR-0021). 결과에 그 값으로 판정했다고 적고,
  부품·비교 페이지에 표시한다. 고르기는 그 값으로 후보를 숨기지 않는다 — 후보 쪽도,
  제약을 만드는 고른 부품 쪽도 (ADR-0016, 이슈 #14·#22)
- **사람이 출처와 함께 고친 값은 적재가 덮지 않고, 다시 「검증 중」으로 세우지도 않는다**
  (이슈 #19)
- 분기 1회 인기 부품 상위 항목 재검증

### 5.6 갱신 부담

| 대상 | 주기 | 방식 |
|---|---|---|
| 신규 CPU/GPU | 출시 시 | 수동. 분기 단위라 감당 가능 |
| 신규 보드/케이스 | 상시 | 사용자 요청 기반. 요청 수가 곧 수요 신호 |
| 단종 처리 | 반기 | `discontinued` 플래그. 삭제하지 않음 |
| 스펙 정정 | 신고 시 | 검토 후 반영 |

**단종 부품을 지우지 않는 이유**는 업그레이드 사용자가 기존 부품을 선택해야 하기 때문이다. 목록에서는 내리되 데이터는 유지한다.

### 5.7.1 국내 유통 매칭 파이프라인 ★

**OpenDB는 글로벌이다. 한국에서 못 사는 부품을 견적에 추천하면 도구로서 실패다.** 따라서 적재 직후 국내 유통 여부를 판정하고, 최종 표시 이름은 수입사가 포함된 국내 상품명을 쓴다.

```
1. OpenDB 적재         글로벌 모델 (parts)
2. 검색 쿼리 생성      모델명 → 핵심 토큰 추출
3. 네이버 쇼핑 조회
4. 후보 필터링         부정 토큰 제거, 변형 토큰 대조
5. 총판 식별           상품명 접미사 → 수입사 매핑
6. SKU 생성            국내 유통 단위 (skus)
7. 유통 판정           유효 SKU 0개 → 미유통 플래그
```

#### 2단계 — 검색 쿼리 생성

풀 모델명으로 검색하면 결과가 0인 경우가 많다. 토큰을 분해해서 조합한다.

```
"ASUS TUF Gaming B650-PLUS WIFI"
  브랜드   ASUS
  핵심모델 B650-PLUS          ← 반드시 포함
  시리즈   TUF, Gaming        ← 선택적
  변형     WIFI               ← 반드시 대조

쿼리: "ASUS B650-PLUS WIFI"  →  결과 0이면  "B650-PLUS 타프"
```

#### 4단계 — 후보 필터링

**변형 토큰 대조가 가장 중요하다.** 놓치면 다른 제품을 같은 것으로 묶는다.

| 구분 | 예시 | 처리 |
|---|---|---|
| 변형 토큰 | WIFI 유무, DDR4/DDR5, 8GB/16GB, OC 에디션 | **완전 일치 요구** |
| 부정 토큰 | 중고, 리퍼, 벌크, 본체, 세트, 브라켓, 케이블 | 제외 |
| 가격 이상치 | 중앙값 대비 극단값 | 제외 후 검토 큐 |

#### 5단계 — 총판 식별

국내 PC 부품 상품명에는 총판명이 거의 항상 접미사로 붙는다. 사전 매칭으로 대부분 잡힌다.

```
"ASUS TUF GAMING B650-PLUS WIFI 대원CTS"        → 대원CTS
"GIGABYTE B760M 어로스 엘리트 피씨디렉트"        → 피씨디렉트
"MSI 지포스 RTX 4070 SUPER 벤투스 ... 이엠텍"    → 이엠텍
```

- ML 불필요. **총판명 사전 + 접미사 매칭**으로 충분
- 미매칭은 검토 큐로 보내 사전을 늘린다
- 주의: 이엠텍처럼 **AIB 브랜드이면서 총판인 경우**가 있다. 브랜드 필드와 혼동하지 않게 구분한다

#### 7단계 — 유통 판정

```
유효 SKU ≥ 1  →  국내 유통 (견적 선택 가능)
유효 SKU = 0  →  미유통 (선택 불가, 호환성 판정에는 여전히 사용)
```

**미유통 부품을 DB에서 지우지 않는다.** 업그레이드 진단(§6.5)에서 사용자의 기존 부품으로 선택되어야 하고, 단종 이력도 데이터로서 가치가 있다.

#### 갱신 주기

| 작업 | 주기 |
|---|---|
| OpenDB sync (git pull) | 주 1회 |
| 신규 부품 유통 판정 | 적재 시 |
| 기존 부품 SKU 재조회 | 주 1회 |
| 가격 갱신 | 인기 부품 일 1회, 나머지 주 1회 |

**유통 중단 감지**: 이전에 SKU가 있었는데 연속 N회 조회에서 0이면 단종 후보로 표시. 즉시 내리지 않고 플래그만 세운다.

### 5.7.2 보조 소스

**제조사 스펙시트** — OpenDB에 없는 필드(특히 물리 치수)를 채운다. 사실 정보라 인용에 문제가 없고, §5.3의 어드민 워크플로로 처리한다.

**GS1 코리안넷** — 기대치 낮음. 특성정보의 치수가 포장 기준이고 부가속성이 식품·가전 중심이라 조립 속성이 정의되어 있을 가능성이 낮다. GTIN을 매칭 키로 쓰는 용도만 검토한다. 코리안넷에서 PC 부품 GTIN 두어 개를 조회하면 5분에 판정된다.

→ **우선순위를 더 내린다.** OpenDB의 `identifiers`에 GTIN/UPC/EAN이 이미 31~85%
들어 있고, 무엇보다 **MPN이 전 카테고리 99% 내외**다. 매칭 키가 필요하면 코리안넷을
거치지 않고 OpenDB의 MPN을 쓰는 편이 낫다 (§5.7.1 참조). 코리안넷 5분 검증은
해도 되지만 Phase 0a의 선행 작업에서는 뺀다.
근거: `docs/research/opendb-schema-analysis.md` §7.6

**Icecat** — OpenDB 커버리지가 충분하면 불필요. 무료 등급은 브랜드 스폰서 제품만 덮고, 모든 제품 페이지에 "Specs Icecat" 표기와 링크, AS IS 면책조항이 요구된다.

**PCPartPicker** — 공식 API 없음, 공개 계획도 없음. 비공식 스크래퍼는 ToS 위반이고 차단당한다. 배제.

참고할 점 하나: 포럼에 **부품이 특정 케이스에 들어가는지 계산해달라는 사용자 요구**가 올라와 있다. 업계 표준 도구조차 물리적 간섭 검증이 약하다는 뜻이며, §4.2가 빈 자리라는 근거다.

### 5.7.3 원칙

**외부 소스를 쓰되 데이터는 자체 보유한다.** 검증된 값은 `source_url`과 함께 우리 DB에 저장한다. OpenDB는 ODC-By라 이 방식에 제약이 없다.

- 벤치마크 수치는 출처를 명시하고 원문을 링크한다
- `[확인 필요: 벤치마크 데이터 인용 범위]`

### 5.8 데이터 모델 초안

```
parts          (id, slug, category, brand, model_name, release_date,
                discontinued, chip_id NULL, opendb_id NULL, mpn NULL,
                manufacturer_url NULL, kr_available, kr_checked_at)
part_specs     (part_id, key, value, unit, source_url, verified_at, disputed)
part_aliases   (part_id, raw_name, confidence, source)

skus           (id, part_id, importer_id NULL, display_name_ko, gtin NULL,
                mall_product_id, first_seen_at, last_seen_at, active)
importers      (id, name, aliases_json, support_url, note)
warranty_policies (importer_id, category, years, method, initial_defect_days,
                source_url, verified_at)
compat_rules   (id, rule_type, severity, condition_json, message_ko)
build_checks   (build_hash, rule_id, result, checked_at)
price_history  (part_id, source, price, mall_name, collected_at)
spec_reports   (id, part_id, spec_key, reported_value, note, created_at)
fps_reports    (id, build_hash, cpu_id, gpu_id, ram_spec_json, game, resolution,
                preset, avg_fps, status, client_token, created_at)
perf_models    (id, version, trained_at, metrics_json, active)
```

`part_specs`를 key-value로 둔 이유는 카테고리마다 스펙 항목이 완전히 달라서다. 컬럼으로 고정하면 부품 종류를 늘릴 때마다 스키마 마이그레이션이 필요해진다. **`autonomous-pipeline-plan.md` §7의 expand-contract 원칙과도 맞는다.**

`parts.chip_id`는 GPU의 AIB 모델이 기준 칩을 참조하기 위한 자기참조다. 칩 레벨 데이터를 상속받고 물리 치수만 덮어쓴다.

단 **1차 소스에는 칩 레벨 레코드가 따로 없다.** OpenDB는 AIB 단일 계층이고 칩은
`chipset` 문자열 필드로만 표현된다 (AIB 3,837개 / chipset 276종). 따라서 `chip_id`는
적재 시 `chipset` 값을 정규화한 slug로 유도하거나, 그 값으로 그룹핑해 칩 레코드를
생성해 채운다. **스키마는 그대로 두고 적재 스크립트에서 해결할 문제다.**
근거: `docs/research/opendb-schema-analysis.md` §7.3

**`parts`와 `skus`의 분리가 핵심이다.** 호환성 판정은 글로벌 스펙(`parts`)에서, 구매 판단과 화면 표시는 국내 유통 단위(`skus`)에서 한다. 견적 결과 화면은 `skus.display_name_ko`를 쓰고, 같은 부품의 수입사별 옵션을 나란히 비교할 수 있다. 보증 정책은 SKU마다가 아니라 수입사마다 정해지므로 `warranty_policies`는 수십 건 규모로 끝난다.

## 6. 성능 분석 (Phase 3)

부품 단위 비교는 이미 여럿 있다(HWbattle, CPUBenchmark 등). **비어 있는 자리는 견적 단위 비교다.** 사용자의 실제 의사결정 단위는 부품이 아니라 완성된 조합이다.

### 6.1 대원칙 — 단일 점수를 만들지 않는다

"이 견적은 87점"은 만들기 쉽고 공유도 잘 되지만, 틀린 답을 자신 있게 내놓는 구조다. 게임은 GPU가, 인코딩·컴파일은 CPU가 지배하므로 용도를 빼고 합산하면 의미가 없다.

**항상 용도 × 해상도 축으로 쪼개서 제시한다.**

```
1080p 게임   |  1440p 게임  |  4K 게임
영상 편집     |  컴파일·빌드  |  일반 사무
```

### 6.2 병목 분석

```
입력: CPU + GPU + 해상도 + 용도
방법: 공개 벤치마크 점수를 정규화 → 해상도별 가중치 적용
출력: "1080p에서는 CPU 제한적, 1440p 이상에서는 균형"
```

- 해상도가 올라갈수록 GPU 의존도가 커지므로 해상도 없는 병목 판정은 의미가 없다
- 게임마다 특성이 달라 일반화에 한계가 있다. 이를 결과에 명시한다
- **단정적 표현을 쓰지 않는다.** "병목입니다"가 아니라 "이 해상도에서는 CPU가 먼저 한계에 닿을 가능성이 높습니다"

### 6.3 견적 대 견적 비교 ★ 핵심 차별점

```
입력: 견적 A, 견적 B (+ 용도, 해상도)
출력:
  - 용도별 상대 성능 (막대 비교, 단일 점수 없음)
  - 가격 차액
  - 차액 대비 성능 이득 평가
  - 어느 부품이 차이를 만들었는지 분해
```

**차이의 크기를 체감 언어로 표현한다.** 숫자만 주면 3% 차이를 큰 것으로 오해한다.

| 성능차 | 표현 |
|---|---|
| ~5% | 체감하기 어려움 |
| 5~15% | 상황에 따라 느낄 수 있음 |
| 15~30% | 뚜렷한 차이 |
| 30%~ | 체급이 다름 |

### 6.4 차액 사용처 제안 ★

견적 비교에서 한 걸음 더 나간 기능. 이것이 진짜 유용한 지점이다.

```
"B가 15만원 비싼데, 1440p 게임 기준 성능 차이는 4%입니다.
 대신 그 예산을 GPU 한 단계 위로 쓰면 같은 용도에서 22% 향상됩니다."
```

- 예산 재배분 시뮬레이션: 총액을 유지하면서 배분만 바꿨을 때의 결과
- 과잉 지출 지적: 이 용도에서 값어치를 못 하는 부품 표시
- 부족 지적: 이 조합에서 발목을 잡는 부품

### 6.5 업그레이드 진단

```
입력: 현재 PC 구성 + 목표 견적
출력: 부품별 교체 효과, 비용 대비 효과 순위
      "GPU만 바꾸면 전체 교체 효과의 80%를 얻습니다"
```

기존 부품을 선택해야 하므로 §5.6에서 단종 부품을 데이터에서 지우지 않기로 한 이유가 여기에 있다.

### 6.6 조합 성능 예측 모델 ★ ML이 실제로 필요한 자리

**문제**: CPU 단독·GPU 단독 벤치마크는 풍부하지만, **특정 CPU+RAM+GPU 조합의 실측 데이터는 존재하지 않는다.** 조합 공간이 수만 개인데 리뷰에서 측정되는 건 수백 개뿐이다. 나머지는 추정할 수밖에 없고, 이것이 이 프로젝트에서 ML이 과장 없이 필요한 지점이다.

#### 6.6.1 구조적 모델 (블랙박스 회귀 아님)

데이터가 적어 순수 회귀는 일반화되지 않는다. **물리 구조를 모델에 반영해 데이터 효율을 높인다.**

```
CPU 한계 FPS = f(코어 수, 클럭, 캐시, IPC 세대, RAM 보정)    해상도 무관
GPU 한계 FPS = g(연산 유닛, 클럭, 메모리 대역폭, VRAM, 해상도)
예측 FPS     ≈ soft-min(CPU 한계, GPU 한계)
```

FPS가 두 한계 중 낮은 쪽에 수렴한다는 것은 알려진 구조다. 이를 사전 지식으로 넣으면 관측되지 않은 조합도 합리적으로 추정되며, 무엇보다 **결과를 설명할 수 있다.**

```
"CPU 한계 145fps, GPU 한계 98fps → 이 해상도에서는 GPU 제한"
```

§6.2의 병목 분석이 별도 기능이 아니라 **이 모델의 부산물**이 된다. 두 한계값의 비교가 곧 병목 판정이다.

#### 6.6.2 RAM 처리

RAM은 CPU 한계에 대한 보정 계수로 다룬다. 독립 변수로 두면 데이터가 부족해 과적합된다.

```
속도(MT/s), 타이밍(CL), 채널 수 → CPU 한계 배율
```

효과가 CPU 아키텍처마다 다르므로(캐시 크기에 따라 민감도가 갈린다) 세대별로 별도 보정을 두되, 데이터가 쌓이기 전에는 보수적으로 잡는다.

#### 6.6.3 모델 선택

- 데이터가 수백~수천 건 규모이므로 **딥러닝은 부적합.** GBM 계열(LightGBM 등) 또는 제약을 건 파라메트릭 모델
- CPU로 학습·추론 가능한 규모. GPU 불필요
- 재학습은 배치로, 데이터가 일정량 쌓일 때마다

#### 6.6.4 불확실성 표시 — 필수

**단일 수치를 내놓지 않는다.**

| 상황 | 표시 |
|---|---|
| 실측 데이터 존재 | "측정값" + 출처 링크 |
| 유사 조합 다수 존재 | "추정 92~104 fps" (좁은 구간) |
| 데이터 희소 영역 | "추정 80~120 fps · 참고용" (넓은 구간) |
| 추정 불가 | 수치를 내지 않고 상대 비교만 |

예측 구간의 폭이 곧 신뢰도 표시다. 데이터 밀도가 낮은 영역에서 넓은 구간이 나오는 건 결함이 아니라 정직함이다.

#### 6.6.5 학습 데이터 — 사용자 제보가 핵심 자산

```
1. 리뷰 사이트 벤치마크     초기 시드. 라이선스 확인 필요
2. 사용자 FPS 제보          ★ 장기 경쟁력
3. 자체 측정                본인 장비 범위 내
```

**2번이 이 프로젝트의 진짜 해자다.** 견적을 만든 사람이 실제 FPS를 제보하면 그것이 곧 학습 데이터가 되고, 리뷰 사이트가 절대 커버하지 못하는 조합들이 쌓인다. 시간이 지날수록 대체 불가능한 자산이 된다.

**제보 설계**
- 견적 결과 화면에 "이 구성 쓰고 계신가요? 실제 FPS를 알려주세요"
- 입력: 게임, 해상도, 옵션 프리셋, 평균 FPS
- 로그인 없이 제보 가능. 브라우저 단위 중복 방지만
- 이상치 자동 필터링 후 검토 큐. 무분별한 학습 반영 금지
- 제보자에게는 "당신의 조합 예측이 이렇게 바뀌었습니다" 피드백

#### 6.6.6 표현 원칙

"AI 분석"이라는 라벨을 전면에 내세우지 않는다. 최근 그 표현은 신뢰의 근거가 아니라 **대충 만들었다는 신호로 읽히며**, 기대치만 올려놓고 실망을 부른다.

대신 이렇게 한다.

- 근거를 그대로 노출: "3DMark Time Spy 기준" + 원문 링크
- 측정값과 추정값을 라벨로 구분
- 예측 구간으로 제시
- 데이터가 부족한 영역은 부족하다고 표시

**틀려도 납득시키는 것은 AI라는 라벨이 아니라 근거의 투명성이다.** 사용자가 수십만 원을 쓰는 결정이므로 "AI라서 틀렸다"는 변명이 통하지 않는다.

### 6.7 공유 구조

견적 비교는 공유 유인이 크다. "이거 봐라" 하고 링크를 던지는 상황이 자연스럽게 생긴다.

```
/vs/:hashA/:hashB          두 견적 비교
/vs/:hashA/:hashB?use=game1440
```

§8의 페이지 구조와 연결되며, 검색 유입에도 기여한다.

### 6.8 데이터 요구사항

이 기능군은 전부 벤치마크 데이터에 의존한다. **시드 데이터가 없으면 Phase 3 자체가 성립하지 않는다.**

- 필요: CPU·GPU별 성능 지표, 가능하면 조합별 실측 FPS
- 출처를 명시하고 원문을 링크한다
- `[확인 필요: 벤치마크 수치 인용 가능 범위, 자체 측정 병행 여부]`
- 시드 확보가 불가능하면 이 Phase를 미룬다. **근거 없는 점수를 지어내지 않는다**

## 7. 상품명 정규화 (Phase 2)

가격 연동의 실질적 난관이자, 이 프로젝트에서 ML이 실제로 필요한 유일한 지점.

### 7.1 문제

네이버 쇼핑 검색에서 "7800X3D"를 조회하면 정품, 병행수입, 멀티팩, 중고, 본체 묶음, 무관한 상품이 섞여 나온다. 이를 같은 부품끼리 묶고 이상치를 걸러야 한다.

### 7.2 단계

```
1. 규칙 필터    제외 키워드(중고, 리퍼, 본체, 세트), 필수 키워드
2. 임베딩       상품명 → 벡터, 등록 부품명과 유사도
3. 이상치 제거  같은 부품 후보들의 가격 분포에서 outlier 제거
4. 대표가 산출  중앙값 사용 (평균은 이상치에 취약)
5. 저장         part_aliases에 매핑 기록, 신뢰도 점수 포함
```

### 7.3 구현 메모

- 임베딩 모델은 작은 다국어 모델로 충분. **CPU로 돌아간다**
- 결과를 캐시하고, 새 상품명이 들어올 때만 추가 연산
- 매칭 신뢰도가 임계 이하면 자동 매핑하지 않고 검토 큐에 넣는다
- **정규화 정확도가 이 기능의 핵심 메트릭이다.** §10에서 파이프라인 판정 기준으로 사용

### 7.4 가격 표시 원칙

- "대략 이 정도" 수준으로만. 정확한 최저가를 표방하지 않는다
- 수집 시각을 반드시 함께 표시
- 구매 링크는 제공하되 최저가 순위를 매기지 않는다
- `[확인 필요: 네이버 오픈 API 이용약관상 데이터 저장·재가공 허용 범위]`

## 8A. 클라이언트 저장 (localStorage)

회원가입 없이 지속성을 확보하는 수단. 서버로 전송하지 않으므로 개인정보 부담이 없다.

### 8A.1 저장 대상

| 키 | 내용 | 상한 |
|---|---|---|
| `builds` | 저장한 견적 목록 | 20개 |
| `recent_builds` | 최근 구성한 견적 (자동) | 5개 |
| `recent_parts` | 최근 조회한 부품 | 20개 |
| `draft` | **작업 중인 견적 (자동)** | 1개 |
| `prefs` | 전기요금 입력값, 해상도, 표시 설정 | — |
| `schema_version` | 저장 포맷 버전 | — |

`prefs`가 체감상 가장 유용하다. 가구 월 사용량 같은 값을 매번 다시 입력하게 만들면 전기요금 기능을 아무도 안 쓴다.

**`draft`는 나중에 추가한 칸이다** (2026-09-21). 새로 고침 한 번에 고른 것이 전부 날아가고 있었다 — 저장 버튼을 눌러야만 남는데, 여러 칸을 채우다 실수로 새로 고치는 것이 바로 그 저장을 하기 전이다.

`recent_builds`를 쓰지 않은 이유는 **뜻이 다르기 때문이다.** 그쪽은 "지나간 구성 목록"이고 이쪽은 "지금 하던 것" 하나다. 섞으면 슬롯을 모두 비운 뒤 새로 고쳤을 때 방금 비운 것이 되살아난다 (`recent_builds`는 부품이 둘 이상일 때만 기록하므로 빈 상태가 남지 않는다).

칸을 **더하는** 것은 §8A.2의 add-only 규칙에 어긋나지 않는다. 기존 칸의 뜻은 그대로고, 구버전 코드는 `draft`를 모른 채 무시한다.

### 8A.2 스키마 버저닝 ★

**서버는 롤백되지만 사용자 브라우저의 데이터는 롤백되지 않는다.** 배포를 되돌려도 구버전 코드가 신버전 데이터를 읽게 되므로, `autonomous-pipeline-plan.md` §7의 가역성 원칙이 클라이언트에는 적용되지 않는다.

따라서 다음을 규칙으로 삼는다.

1. **저장 포맷은 add-only.** 필드를 추가할 수는 있어도 의미를 바꾸거나 제거하지 않는다 (서버 스키마의 expand-contract와 같은 원칙)
2. **읽기는 관대하게.** 모르는 필드는 무시하고, 없는 필드는 기본값으로 채운다. 구버전 코드가 신버전 데이터를 만나도 깨지지 않아야 한다
3. **모든 레코드에 `v` 필드.** 읽을 때 버전을 보고 필요하면 마이그레이션
4. **파싱 실패는 조용히 폐기.** 견적 하나가 깨졌다고 앱 전체가 죽으면 안 된다. try/catch로 감싸고, 실패한 항목만 버린다
5. **포맷 변경은 T2로 분류.** 되돌릴 수 없는 변경이므로 승인 대상이다

```javascript
// 읽기 패턴
function loadBuilds() {
  try {
    const raw = localStorage.getItem('builds');
    if (!raw) return [];
    const parsed = JSON.parse(raw);
    return parsed
      .map(migrate)          // 버전별 마이그레이션
      .filter(Boolean);      // 복구 불가 항목 제거
  } catch {
    return [];               // 앱은 계속 동작
  }
}
```

### 8A.3 URL이 진실 소스

localStorage는 편의 기능이고, **견적의 정본은 공유 URL이다.**

- 저장된 견적은 각각 공유 URL을 함께 보관한다
- 브라우저 데이터를 지우면 사라진다는 점을 UI에 명시하고, 백업 방법으로 URL 복사를 안내한다
- 견적 목록 전체를 JSON으로 내보내기/가져오기 (Phase 1)

이 구조 덕분에 localStorage가 완전히 날아가도 사용자는 URL만 있으면 복원할 수 있다.

### 8A.4 주의

- 시크릿 모드, 스토리지 차단 설정, 용량 초과 시 쓰기가 실패한다. **저장 실패를 정상 경로로 처리**하고, 실패 시 "이 브라우저에서는 저장할 수 없습니다" 정도로 안내
- 저장 상한을 두고 초과 시 오래된 것부터 제거 (LRU)
- 개별 항목이 아니라 목록 전체를 한 키에 담는다. 키를 잘게 나누면 일관성 깨진 상태가 생긴다

## 9. 기술 스택

**확정됨** — ADR-0010. 선정 근거와 탈락 대안은 `docs/research/stack-requirements.md`.

| 구분 | 확정 |
|---|---|
| **프론트·백엔드** | **Next.js (TypeScript)** — App Router, SSR/ISR |
| **DB** | **PostgreSQL** — JSONB로 `part_specs` 처리 |
| **규칙 엔진** | 프레임워크 비의존 **순수 TS 모듈.** 클라이언트·서버 공유 |
| **정규화 워커** (Phase 2) | Python 별도 서비스. DB로만 연결 |
| **캐시** | **두지 않는다.** 부하가 없다 |

- **SSR 또는 정적 생성은 요구사항이다.** 검색 유입이 목적이므로 CSR 단독은 불리하다.
  `/part/:slug` 롱테일이 부품 수(적재 대상 20,282건)만큼 생기므로 빌드타임 전량 생성은
  비현실적이다 → ISR로 처리한다
- **규칙 엔진을 한 벌만 유지하는 것이 이 선택의 핵심 이유다.** 견적 편집 중 즉시 판정과
  `/build/:hash` SSR 결과가 같은 코드를 쓴다. 두 벌이면 "편집 중엔 통과인데 공유
  링크에선 오류"가 나고, 규칙이 8개에서 14개로 늘 계획(§4.2)이라 어긋날 여지가 커진다

부하가 거의 없는 서비스다. 최적화를 미리 하지 않는다.

## 10. 파이프라인 연계

`autonomous-pipeline-plan.md`와의 접점.

### 10.1 합성 트래픽 시나리오 (§9.5)

배포 게이트와 상시 관측에 사용할 엔드투엔드 시나리오.

1. 견적 구성 → 호환성 체크 → 결과 확인
2. 의도적으로 충돌하는 조합 → 오류가 정상 검출되는지
3. 부품 상세 페이지 조회
4. 전력·전기요금 계산
5. 견적 공유 링크 생성 → 재방문
6. 견적 저장 → 페이지 이탈 → 재방문 시 복원 확인
6b. 두 견적 비교 페이지 진입 (Phase 3 이후)
7. 구버전 포맷 데이터를 심어둔 상태로 진입 → 마이그레이션 동작 확인
8. 가격 수집 잡 1회 실행 (Phase 2 이후)

### 10.2 자연 발생 장애 (§12.2 표본 확보)

카오스 주입 없이도 실제 장애가 생기는 지점들.

- 외부 API 쿼터 초과, 응답 지연, 스키마 변경
- OpenDB 업스트림 스키마 변경으로 적재 실패
- 국내 유통 매칭 실패율 상승 (상품명 표기 변화)
- 가격 수집 배치 잡 실패
- 정규화 매칭 품질 저하
- 부품 데이터 증가에 따른 쿼리 성능 저하

### 10.3 기능 단위 비활성화 (§6.3 시도 3단계)

기능이 독립적이라 하나를 꺼도 나머지가 살아남는다. feature flag 설계에 유리하다.

```
가격 표시 off      → 호환성·전력은 정상 동작
성능 분석 off      → 호환성·전력·가격은 정상 동작
전기요금 off       → 나머지 정상
비교 페이지 off    → 견적 도구는 정상
```

### 10.4 검증 기준 (§9.3)

- 호환성 규칙: 각 규칙마다 통과/실패 케이스 고정. **회귀 테스트의 핵심**
- **판정 불가: 필요 필드를 비운 부품으로 각 규칙이 "통과"가 아니라 "판정 불가"를
  내는지 검증한다.** 결측이 조용히 통과로 바뀌는 회귀가 가장 위험하다 (§4.3)
- 전력 계산: 알려진 조합의 기대값 대조
- 정규화: 수동 검증한 정답 세트 대비 정확도. 임계 이하면 배포 차단
- **localStorage 마이그레이션: 과거 모든 버전의 샘플 데이터를 보관하고, 배포마다 전 버전이 정상 복원되는지 검증**
- 성능 예측 모델: 홀드아웃 세트 대비 오차. 기준 초과 시 이전 모델 버전 유지, 배포 차단

### 10.5 클라이언트 데이터의 롤백 비대칭 ★

**배포를 롤백해도 사용자 브라우저의 localStorage는 되돌아가지 않는다.** 서버 코드만 구버전으로 복귀하고 데이터는 신버전 포맷으로 남는다. `autonomous-pipeline-plan.md` §7이 다루는 가역성은 서버 측 이야기이며, 클라이언트에는 적용되지 않는다.

- 저장 포맷 변경은 **T2(승인 필수)** 로 분류한다
- 자가수복 루프가 저장 포맷을 임의로 바꾸지 않도록 §6.5 즉시조치 화이트리스트에서 제외한다
- 회귀 테스트에 **구버전 데이터를 심어둔 상태에서의 동작**을 반드시 포함한다. 이것이 유일한 방어 수단이다
- 카오스 카탈로그에 "잘못된 포맷의 localStorage 데이터" 항목을 추가한다

### 10.6 안전성

금전 거래 없음, 개인정보 없음, 로그인 없음. **자가수복이 로직을 잘못 고쳐도 사용자 피해가 없다.** §12.1의 범위 개방을 진행하기에 적합한 성격이다.

## 11. 로드맵

각 Phase가 곧 배포 단위이자 파이프라인 검증 대상이다.

| Phase | 내용 | 데이터 | 완료 기준 |
|---|---|---|---|
| **0a** | **OpenDB 적재 + 유통 매칭 + 어드민** | OpenDB clone | 국내 유통 부품 목록 확보, 빈 필드 보강 흐름 |
| 0b | 호환성 체크 + 전력 계산 | 부품 100개 | 규칙 8개 동작, 견적 공유·저장 |
| 1 | 전기요금, 쿨러·스토리지 추가 | 150개 | 누진세 계산 검증 |
| 2 | 가격 연동 + 정규화 | 150개 | 정규화 정확도 기준 충족 |
| 3 | 성능 분석 (병목·견적비교·업그레이드) | 벤치마크 시드 + FPS 제보 | 용도별 비교, 예측 구간 제시 |
| 4 | 가격 통계 지표 | 6개월 이력 | 백분위·변동성 표시 |
| 5 | 계절성 분석 | 1년 이력 | — |

**0a를 0b보다 먼저 만든다.** 견적 도구가 아무리 잘 돌아도 데이터가 없으면 빈 화면이고, 입력이 불편하면 100개를 채우다 지친다. 이 순서를 바꾸면 프로젝트가 데이터 단계에서 멈춘다.

**예측 모델은 로드맵에 없다.** 1년 이력이 쌓인 뒤 재검토한다. 틀린 예측은 사용자에게 금전 손해를 입히므로, 확신이 설 때까지 기술통계로만 답한다.
