# 호환성 규칙 명세 (Phase 0)

`pc-builder-spec.md` §4.1의 필수 규칙 8개를 구현 가능한 수준으로 확정한 문서다.
**규칙 엔진을 구현하기 전에 이 문서를 읽는다** (CLAUDE.md 작업 규칙 1).

- 상위 문서: `pc-builder-spec.md` §4 (규칙 목록·판정 등급)
- 근거 조사: `docs/research/opendb-schema-analysis.md`
- 관련 ADR: ADR-0002 (OpenDB 1차 소스), ADR-0009 (판정 불가 등급)

> 필드 경로는 전부 **BuildCores OpenDB 스키마 기준**이다 (clone 커밋 `4880970`).
> 자체 DB 스키마(`pc-builder-spec.md` §5.8)로 적재한 뒤에는 `part_specs`의 key로
> 대응되며, 그 매핑은 적재 스크립트(이슈 #3)가 정의한다.

## 0. 공통 규약

### 0.1 판정 결과는 3값이다

ADR-0009에 따라 규칙 하나의 평가 결과는 boolean이 아니다.

```
pass     조건을 만족한다
fail     조건을 위반한다        → 등급은 규칙별로 오류 / 경고
unknown  판정에 필요한 데이터가 없거나 신뢰할 수 없다  → 판정 불가
```

`unknown`에는 **어느 부품의 어느 필드 때문인지**가 실려야 한다. 화면에도 그대로 나간다.

```
unknown:
  rule: 6
  missing: [{ part: "NZXT H5 Flow", field: "케이스 지원 PSU 폼팩터" }]
```

### 0.2 `unknown` 판정 조건은 세 가지다

| 유형 | 정의 | 예 |
|---|---|---|
| **결측** | 필드가 `null`이거나 빈 배열·빈 문자열 | 케이스 `supported_power_supply_form_factors: null` |
| **모순** | 값은 있으나 다른 필드와 물리적으로 양립 불가 | GPU `tdp: 575` + 커넥터 전부 `0` (§8.4) |
| **범위 밖** | 값이 스키마 enum이나 상식 범위를 벗어남 | `releaseYear: 20117` |

**결측만 검사하면 안 된다.** OpenDB에는 미입력을 `0`으로 채운 레코드가 실재하며,
`0`은 결측 검사를 통과해 **거짓 pass를 만든다.** 이것이 이 도구의 최악의 실패 모드다.

### 0.3 적용 순서

규칙 간 의존이 없으므로 순서는 자유다. 단 **화면 표시 순서는 번호순**으로 고정해,
같은 견적에 대해 항상 같은 순서로 보이게 한다.

## 1. CPU 소켓 = 메인보드 소켓

| | |
|---|---|
| **등급** | 오류 |
| **입력** | `CPU.socket` · `Motherboard.socket` |
| **충전율** | 100% / 100% (현행 세대) |

```
pass     CPU.socket == Motherboard.socket
fail     그 외
unknown  둘 중 하나라도 결측
```

**함정 없음.** 두 필드가 **같은 enum 51개 값 집합**을 공유하므로 정규화 없이
문자열 완전 일치로 판정한다. 매핑표를 만들지 않는다.

> 메시지 — fail: "CPU 소켓(AM5)과 메인보드 소켓(LGA1700)이 다릅니다. 장착되지 않습니다."

## 2. 메모리 규격 일치

| | |
|---|---|
| **등급** | 오류 |
| **입력** | `RAM.ram_type` · `Motherboard.memory.ram_type` · `CPU.specifications.memory.types[]` |
| **충전율** | 100% / 100% / 100% (현행 세대) |

```
pass     RAM.ram_type == Motherboard.memory.ram_type
         AND RAM.ram_type ∈ CPU.specifications.memory.types
fail     그 외
unknown  RAM 또는 메인보드 값이 결측
```

**CPU 쪽은 보조 검사다.** `CPU...memory.types`가 결측이면(전체 10.8%) 그 항목만 건너뛰고
메모리↔메인보드 일치만으로 판정한다. CPU 결측 하나로 전체를 `unknown`으로 만들지 않는다.
단 **건너뛰었다는 사실을 결과에 남긴다.**

> 메시지 — fail: "이 메모리는 DDR4인데 메인보드는 DDR5만 지원합니다."

## 3. 메모리 모듈 수 ≤ 슬롯 수

| | |
|---|---|
| **등급** | 오류 |
| **입력** | `RAM.modules.quantity` · `Motherboard.memory.slots` |
| **충전율** | 100% / 100% (현행 세대) |

```
pass     Σ(선택한 키트별 modules.quantity) <= Motherboard.memory.slots
fail     그 외
unknown  둘 중 하나라도 결측
```

**여러 키트를 담을 수 있으므로 합산이다.** 스펙 §3의 MVP는 메모리 1종 선택이지만,
엔진은 처음부터 합산 구조로 만든다. 나중에 키트 2개 선택을 허용할 때 규칙을 다시
쓰지 않아도 된다.

**함께 낼 정보 (등급: 정보)**: 모듈 수가 슬롯 수보다 적고 홀수가 아니면
"듀얼 채널로 동작하려면 2의 배수로 채우는 것이 좋습니다" 수준의 안내. 판정은 아니다.

## 4. GPU 길이 ≤ 케이스 GPU 최대 길이

| | |
|---|---|
| **등급** | 오류 (여유 구간은 경고) |
| **입력** | `GPU.length` · `PCCase.max_video_card_length` (둘 다 mm) |
| **충전율** | 100% / 97.4% (현행 세대) |

```
pass     GPU.length <= max * 0.95
경고     max * 0.95 < GPU.length <= max
fail     GPU.length > max
unknown  둘 중 하나라도 결측
```

**95% 임계는 스펙 §5.1의 결정이다.** 제조사 표기가 낙관적이어서 전면 팬이나 케이블
때문에 표기값 그대로는 안 들어가는 경우가 많다.

> 메시지 — 경고: "GPU 길이 336mm, 케이스 한계 340mm입니다. 빠듯할 수 있고 전면 팬이나
> 케이블 정리에 따라 안 들어갈 수 있습니다."

### 4.1 칩만 선택한 경우

AIB 모델을 지정하지 않으면 이 규칙은 **`unknown`**이고, 대신 범위만 안내한다.
단정하지 않는다 (`pc-builder-spec.md` §5.1).

**범위는 OpenDB에서 계산해 쓴다.** chipset별 AIB `length` 분포의 min~max를 적재 시
집계해 두면 된다. 실제 분포를 확인해보면 범위 안내가 왜 필요한지 분명하다.

| chipset | AIB 수 | 최소 | 중앙값 | 최대 | 스프레드 |
|---|---|---|---|---|---|
| RTX 5060 | 72 | 145mm | 228mm | 329mm | **184mm** |
| RTX 4060 Ti 8GB | 53 | 170mm | 250mm | 338mm | 168mm |
| RTX 5080 | 77 | 220mm | 329mm | 385mm | 165mm |
| RTX 4090 | 61 | 203mm | 336mm | 360mm | 157mm |
| RTX 4070 | 86 | 201mm | 300mm | 342mm | 141mm |
| RTX 4070 SUPER | 59 | 227mm | 269mm | 342mm | 115mm |

스펙 §5.1이 "같은 4070이라도 240mm에서 340mm까지 벌어진다"고 한 관찰은 정확했고,
실제로는 **더 넓다**(201~342mm). 칩만으로 길이를 판정할 수 없다는 근거다.

> 메시지 — unknown: "RTX 4070은 모델에 따라 201~342mm로 차이가 큽니다.
> 정확한 판정을 위해 구체적인 모델을 선택하거나 길이를 직접 입력해 주세요."

AIB를 고르면 §4의 확정값 판정으로 넘어간다.

## 5. 메인보드 폼팩터 ⊂ 케이스 지원 목록

| | |
|---|---|
| **등급** | 오류 |
| **입력** | `Motherboard.form_factor` · `PCCase.supported_motherboard_form_factors[]` |
| **충전율** | 100% / 100% (현행 세대) |

```
pass     Motherboard.form_factor ∈ PCCase.supported_motherboard_form_factors
fail     그 외
unknown  둘 중 하나라도 결측
```

**정규화 불필요.** 두 enum이 정확히 같은 12개 값이다 — 조사에서 대조 확인했다.

```
ATX, Micro ATX, Mini-ITX, EATX, Mini DTX, DTX,
SSI EEB, SSI CEB, XL ATX, HPTX, Thin Mini-ITX, Flex ATX
```

**주의: `PCCase.form_factor`와 혼동하지 않는다.** 그건 케이스 자체의 분류
(`ATX Mid Tower` 등 17개 값)이고, 판정에 쓰는 것은
`supported_motherboard_form_factors` 배열이다.

**하위 호환을 임의로 가정하지 않는다.** ATX 케이스가 대체로 Micro ATX를 수용하지만,
그건 `supported_motherboard_form_factors`에 실제로 들어 있을 때만 참이다. 배열에
없으면 `fail`이다. 추론으로 통과시키지 않는다.

## 6. PSU 폼팩터 ⊂ 케이스 지원 ★ 데이터가 가장 부족한 규칙

| | |
|---|---|
| **등급** | 오류 |
| **입력** | `PSU.form_factor` · `PCCase.supported_power_supply_form_factors[]` |
| **충전율** | 100% / **16.8%** (현행 세대) ← **83.2% 결측** |

```
pass     PSU.form_factor ∈ PCCase.supported_power_supply_form_factors
fail     그 외
unknown  케이스 쪽 결측 (현행 세대 케이스의 83.2%)
```

enum은 양쪽 7개 값이 정확히 일치한다: `ATX, SFX, SFX-L, TFX, Flex ATX, Mini-ITX, ATX/EPS`

**Phase 0 초기에는 이 규칙이 대부분 `unknown`으로 뜬다.** 정상 동작이다.
케이스 보강(이슈 #6 어드민)이 진행될수록 줄어든다.

**절대 하지 말 것**: 케이스가 ATX 보드를 지원한다는 이유로 ATX PSU도 지원한다고
추론하기. 상관관계는 높지만 SFX 전용 케이스가 실재하고, 틀리면 사용자가 못 쓰는
파워를 산다.

> 메시지 — unknown: "이 케이스가 지원하는 파워 규격 정보가 아직 없어 판정하지
> 못했습니다. 제조사 스펙을 직접 확인해 주세요." + 보강 요청 버튼

### 6.1 판정 불가에 덧붙이는 참고 분포 (ADR-0013)

판정은 `unknown` 그대로 두되, 같은 `form_factor`에서 **관측된** 지원 분포를
`notes` 한 줄로 덧붙인다. 판정을 바꾸지 않으므로 거짓 통과가 생기지 않는다.

> 참고: BuildCores OpenDB PCCase 전수 3,782건에서 Mini ITX Tower 중 값이 확인된
> 17건은 SFX 14건(82%), SFX-L 14건(82%), ATX 2건(12%), Flex ATX 1건(6%)이었습니다.
> 이 케이스의 사양이 아니라 같은 폼팩터의 관측 분포입니다 (측정일 2026-09-19).

- 분포표: `packages/compat/src/case-reference.ts` — 정적 상수. 엔진은 DB를 쓰지 않는다
- 측정 근거와 재현 절차: `docs/research/case-psu-formfactor-distribution.md`
- **표본 10건 미만은 인용하지 않는다.** 4건의 100%가 401건의 99%보다 세 보이는
  착시를 만들지 않는다. 데이터가 0건인 폼팩터(HTPC·Desktop·테스트벤치)도 같다
- 해당 케이스의 값이 채워지면 이 문장은 자동으로 사라진다

이 패턴은 규칙 6에만 쓴다. 다른 규칙으로 넓히려면 그때 근거를 따로 만든다.

## 7. 소비전력 대비 PSU 정격 — 구간 판정

| | |
|---|---|
| **등급** | 오류 / 경고 (구간에 따라) |
| **입력** | `CPU.specifications.tdp`·`ppt` · `GPU.tdp` · `PSU.wattage` + **범위 가정** |
| **충전율** | 100% / 100% / 100% (현행 세대) |

### 7.1 메인보드 소비전력 필드는 존재하지 않는다

`pc-builder-spec.md` §4.1이 필요 데이터로 적었던 "보드 파워"는 **OpenDB 메인보드
스키마에 없다.** `tdp` / `wattage` / `power_draw`를 전부 검색해 확인했다.
`power_connectors`는 커넥터 종류(`24-pin`)일 뿐 W가 아니다.

따라서 **CPU와 GPU만 실측값을 쓰고 나머지는 가정한다.**

```
CPU 전력 = specifications.ppt 가 있으면 ppt, 없으면 tdp
GPU 전력 = tdp
```

`ppt`를 우선하는 이유는 그것이 실측 최대에 가깝고 TDP가 실사용 피크를 과소평가하기
때문이다 (현행 세대 CPU 98.3% 충전).

### 7.2 가정은 점 값이 아니라 범위다 ★

공개 자료의 편차가 크다 — 메인보드는 **25~80W로 3배 차이**다. 점 값을 하나 고르는
것은 근거 없는 수치를 만드는 것이고, 이 규칙은 오류 등급이라 틀리면 사용자가 멀쩡한
파워를 못 쓴다고 판단하거나 부족한 파워를 괜찮다고 믿는다.

ADR-0004·§6.6.4의 원칙을 그대로 적용한다 — **단일 수치를 내놓지 않는다.**

| 항목 | 범위 | 출처 |
|---|---|---|
| 메인보드 | 25 ~ 80 W | Seasonic PSU 계산기 가이드 ⚠ 원문 미확인 |
| 메모리 (모듈당) | 2 ~ 5 W | 〃 |
| 여유분 배수 | 1.3 | `pc-builder-spec.md` §4.1. Seasonic의 20~30%와 일치 |

**⚠ 원문 미확인**: 이 실행 환경의 네트워크 정책이 `seasonic.com`을 차단해 1차 출처를
직접 읽지 못했다. 검색 결과가 해당 페이지의 수치로 제시한 값이다. 경위는
`docs/research/power-constants.md`. **출처 라벨에 이 미검증 상태를 함께 노출한다.**

스토리지·쿨러·팬은 MVP 취급 부품(6종)에 없으므로 가정하지 않는다. Phase 1에서
해당 부품이 견적에 들어올 때 확정한다.

### 7.3 판정식

```
모듈수   = Σ(선택한 키트별 module_count)
총_최소  = CPU + GPU + 보드_최소 + 메모리_최소 × 모듈수
총_최대  = CPU + GPU + 보드_최대 + 메모리_최대 × 모듈수
권장정격 = ceil(총_최대 × 1.3)

pass     PSU.wattage >= 권장정격                    여유 있음
경고     총_최소 <= PSU.wattage < 권장정격          가정에 따라 갈림
fail     PSU.wattage < 총_최소                      가정을 아무리 낮게 잡아도 부족
unknown  CPU/GPU 전력 또는 PSU 정격 결측
```

- GPU를 고르지 않았으면 GPU 전력은 0이다 (내장그래픽 구성)
- 메모리를 고르지 않았으면 모듈수는 0이다
- **경계 구간이 넓은 것은 결함이 아니다.** 가정 범위가 좁혀지면 경고 구간도 줄어든다

### 7.4 표시 원칙

**가정 범위와 출처를 결과에 함께 낸다.** §7.2의 원문 미확인 상태도 숨기지 않는다.
사용자가 왜 그 판정이 나왔는지 확인할 수 있어야 한다.

> 메시지 — 경고: "총 소비전력 약 551~612W로 추정됩니다. 권장 정격은 796W인데
> 750W라 가정에 따라 갈립니다. (메인보드 25~80W, 메모리 모듈당 2~5W로 가정)"

## 8. PCIe 보조전원 커넥터 수 충족 ★ 정규화와 모순 검사 필요

| | |
|---|---|
| **등급** | 오류 |
| **입력** | `GPU.power_connectors.*` · `PSU.connectors.*` |
| **충전율** | 96.7~100% / 100% (현행 세대) |

### 8.1 GPU와 PSU의 커넥터 표현이 비대칭이다

| 커넥터 | GPU 쪽 | PSU 쪽 |
|---|---|---|
| 6핀 | `pcie_6_pin` | `pcie_6_plus_2_pin` — 6핀·8핀 **통합 카운트** |
| 8핀 | `pcie_8_pin` | 위와 같은 필드 |
| 16핀 | `pcie_12VHPWR` **와** `pcie_12V_2x6` **분리** | `pcie_12vhpwr` **하나뿐** |

PSU의 6+2핀 커넥터는 6핀 요구와 8핀 요구 양쪽을 충족한다. GPU의 12VHPWR과 12V-2x6은
핀 배열이 호환되므로(ATX 3.0 vs 3.1) PSU 쪽에서는 구분하지 않는다.

### 8.2 정규화 후 판정식

```
GPU_8pin류  = (pcie_8_pin  ?? 0) + (pcie_6_pin ?? 0)
GPU_16pin류 = (pcie_12VHPWR ?? 0) + (pcie_12V_2x6 ?? 0)

pass     PSU.connectors.pcie_6_plus_2_pin >= GPU_8pin류
         AND PSU.connectors.pcie_12vhpwr  >= GPU_16pin류
fail     그 외
unknown  §8.3 또는 §8.4에 해당
```

### 8.3 결측 판정

GPU 커넥터 4필드 중 **하나라도 `null`이면 `unknown`**이다. 현행 세대 GPU의 43건이
부분 null이다. `null`을 0으로 간주하지 않는다 — 그러면 §8.4의 거짓 통과가 된다.

### 8.4 ★ 모순 검사 — `0`을 그대로 믿지 않는다

**조사에서 확인된 실제 데이터 문제다.** 적재 후 전수 집계한 결과는 처음 추정보다
훨씬 나쁘다.

| 범위 | 모순 건수 |
|---|---|
| RTX 40/50 (조사 시 표본) | 166 / 1,069 |
| **GPU 전체 (TDP > 75W)** | **705 / 3,468 = 20.3%** |

**TDP가 75W를 넘는 GPU 다섯 중 하나꼴로 커넥터가 전부 명시적 `0`이다.**
RTX 5090(TDP 575W)도 포함된다.

PCIe 슬롯이 공급할 수 있는 전력은 **75W**다. 그보다 많이 먹는 카드는 보조전원이
반드시 필요하므로, 이 조합은 **물리적으로 불가능하며 데이터 오류다.**

```
if GPU.tdp > 75 AND GPU_8pin류 == 0 AND GPU_16pin류 == 0:
    → unknown (사유: 커넥터 정보 오류로 판단됨)
```

**이 검사가 없으면 166건이 "보조전원 0개 필요 → 통과"로 처리된다.** 결측 검사만으로는
잡히지 않는다. 값이 `null`이 아니라 `0`이기 때문이다.

> 이 사례가 ADR-0009의 근거다. 결측을 통과로 처리하는 것뿐 아니라, **잘못된 값을
> 통과로 처리하는 것**도 막아야 한다.

### 8.5 알려진 소수 이상치

| 패턴 | 건수 | 처리 |
|---|---|---|
| `12VHPWR: 1` **그리고** `12V_2x6: 1` | 2 | 합산하면 16핀 2개를 요구하게 된다. 중복 기입 의심 → `unknown` |
| `12VHPWR: 2` | 1 | 소비자용 카드에 16핀 2개는 이례적 → `unknown` |

**보수적으로 `unknown`을 택한다.** 둘 다 극소수라 실사용 영향이 작고, 잘못 통과시키는
비용이 판정을 미루는 비용보다 크다.

## 9. CPU 쿨러 높이 ≤ 케이스 최대 높이 (Phase 1)

| | |
|---|---|
| **등급** | 경고 |
| **입력** | `CPUCooler.height` · `CPUCooler.water_cooled` · `PCCase.max_cpu_cooler_height` |
| **충전율** | 70.4% / 99.9% / **35.2%** |

명세: `pc-builder-spec.md` §4.2 규칙 9. **공랭에만 적용한다.**

```
skip     water_cooled = true       수랭은 높이가 아니라 라디에이터 문제다 (규칙 10, Phase 2)
pass     쿨러 높이 ≤ 케이스 한계
warning  쿨러 높이 > 케이스 한계
unknown  어느 한쪽 결측
```

### 9.1 오류가 아니라 경고인 이유

명세 §4.2가 이 규칙을 경고 등급에 둔다. 제조사가 재는 "최대 높이"는 사이드 패널까지의
여유를 얼마나 보수적으로 잡았는지에 따라 달라지고, 팬 위치를 옮기거나 패널을 바꿔
들어가는 사례가 실재한다. **오류로 단정하면 실제로는 쓸 수 있는 조합을 막는다.**

반대로 규칙 4(GPU 길이)는 오류다. GPU는 슬롯에 고정되므로 조정 여지가 없다.
같은 "길이 비교"지만 등급이 다른 이유가 이것이다.

### 9.2 수랭을 건너뛰되 건너뛴 사실은 남긴다

`water_cooled = true`면 이 규칙은 `RuleResult.skipped`에 사유를 남기고 판정하지
않는다. 통과로 표시하지 않는다 — 라디에이터가 들어가는지는 **아직 아무도 확인하지
않았다.** 규칙 10이 Phase 2 이후라 그 확인은 지금 불가능하다 (명세 §4.2).

`water_cooled`가 결측이면 수랭 여부를 모르므로 `unknown`이다. 높이가 있다고
공랭으로 단정하지 않는다 — AIO에도 `height`가 채워진 레코드가 있다.

### 9.3 여유 구간을 경고로 올리지 않는다

규칙 4는 95% 이상을 "빠듯함" 정보로 알린다. 여기서는 하지 않는다.
케이스 한계값 자체가 35.2%만 채워져 있고 보수성도 제각각이라, 그 위에
다시 5% 경계를 얹으면 근거 없는 정밀도를 주장하게 된다.

### 9.4 부품 슬롯 추가

이 규칙을 쓰려면 견적에 CPU 쿨러 슬롯이 생긴다. 따라오는 변경:

- 공유 코드 **v2** — 슬롯이 하나 늘어난다. **v1 디코더는 그대로 둔다** (ADR-0012)
- `localStorage` 저장 포맷에 `cooler` 필드 추가 — add-only (ADR-0005)
